# Scrapkeep project instructions

Scrapkeep is a Godot roguelite at `sketches/core-loop` with three worlds. The goal is a finished-feeling Linux alpha. World 1 (the Spillway) comes first; worlds 2 and 3 are parked. Andrew plays a world 1 sitting, then one full-alpha sitting, and no wave asks him to play. One local Claude Code session on Andrew's PC coordinates the work and is the Gate (ruling ds, 15 Nov 2026): it talks to Andrew in its own chat and builds each unit itself or through a writer agent in a separate worktree. The rules below say "thread" from the claude.ai project period (ruling dh, 12 to 14 Nov); they bind the local session and its writer agents the same way. Andrew's personal A stack plugin preferences and host policy still apply.

## Read first, in this order

1. [START-HERE.md](project-guide/handoff/START-HERE.md): who owns what, and where to go for each kind of work.
2. [STATE.md](project-guide/handoff/STATE.md): the open stage and the live board. Alpha work stacks on `stage/alpha-w<N>`.
3. Your brief, the exact sources it names, and the rows of [DECISIONS.md](project-guide/handoff/DECISIONS.md) it cites. The newest ruling wins. Do not ask Andrew a question that is already ruled.

Read the rest only when the task needs it: [ROADMAP.md](project-guide/handoff/ROADMAP.md) for the order of what is left, [CONTRIBUTING.md](CONTRIBUTING.md) for commands, [ORCHESTRATOR.md](ORCHESTRATOR.md) for the gate, and the one section of [LESSONS.md](project-guide/handoff/LESSONS.md) that covers your work.

## Rules, most important first

1. **Finish every to-do** (ruling dn, Andrew, 14 November 2026). Keep going until every task is done, including tasks Andrew or the coordinator add later. Before you say "done" or go idle, read the original ask again and list each task as done (with its pull request or file), handed off (to whom) or not done. Finish what is not done. A PC session waits on a background job for at most about 45 minutes, then takes a short turn ([DEVICES.md](project-guide/handoff/DEVICES.md)).
2. **One thread, one writer** (ruling by). A project thread writes its own changes, runs its own checks and owns its pull request from claim to merge. It starts a sub-agent only for work that writes nothing and returns a short finding: wide search, research, a long noisy run, and the independent review of its finished diff. Work too big for one thread goes to the coordinator to split.
3. **Only the Gate stacks** (ruling ds, 15 Nov 2026). One local Claude Code session on Andrew's PC is the coordinator and the Gate. It alone stacks pull requests onto the stage, runs the wave gate, promotes, and runs the PC work. A writer agent it starts opens a draft pull request against the open stage and reports back; "the board thread" in older pages means this session.
4. **Every pull request gets focused tests, `npm run sketch:fast -- --base <stage>` and one independent review.** The wave gate runs once per promotion and the release gate once per sprint. [ORCHESTRATOR.md](ORCHESTRATOR.md)'s tiered gate is the only owner of that rule. Rerun a red alone before you call it red ([GATE.md](project-guide/handoff/GATE.md)).
5. **Write for a reader with no context** (ruling cz). Every board post, receipt, brief, report and hand-off stands on its own, leads with what changed or what the reader must do, and uses plain words with no term made up during the work. A cloud session cannot see the PC's disk, so name a pushed branch, a pull request or a repo file, never a local path alone. [COMMS.md](project-guide/handoff/COMMS.md) has the rules.
6. **One home for every fact** (ruling bz). Update the page that exists before you make a new one, link instead of repeating, and add anything new to the library in the same turn.
7. **Deep modules, simple interfaces** (Andrew, 9 November 2026). Put new behaviour inside the module that owns the state and give callers one small call, never a reach into private members. Do not widen an interface to save a few lines. [DEEP-SWEEP.md](project-guide/handoff/DEEP-SWEEP.md) has the method.
8. **No slop in anything the player meets** (ruling cx). Before a word goes on a screen, ask whether position, shape, colour, an icon, motion or sound should carry the fact instead. No eyebrow labels, no heading that restates the screen, no label that restates its value, one name for one thing, no filler. Keep the game's voice. [LEGIBILITY.md](sketches/core-loop/design-v3/LEGIBILITY.md) section 13 has the pattern list and the carrier order; a change a player can read or navigate is written and reviewed against it.
9. **World 1 design directions** (rulings ct, cu and cv). Every map is held to the ten-point map standard. Difficulty is tuned harder, never easier: hardness presses a ball that slows or stops, and never stops a ball that keeps rolling and turning. A world plays as one ride with no hard cut between stages. Read the audit for the area in [shared/world1/](project-guide/handoff/shared/world1/) before you change a map, the difficulty or a hand-over.
10. **Read the story and tone first for creative work**: [STORY-MAP.md](sketches/core-loop/design-v3/STORY-MAP.md) and [the tone bible](project-guide/handoff/shared/tone/TONE-BIBLE.md) before design, art or sound.
11. **Models by tier, not by version** (ruling bp). The definitions in `.claude/agents` own the pins: the fast tier at medium for search, lookup and a fully specified mechanical unit (as a whole thread, or in a local coordinator session), the mid tier at medium for routine review, the acceptance gate and work that only runs and compares tests, the top tier at high for judgement and consequential review. The pins are family aliases, so each tier runs its newest model. Nothing runs above high. Claude project agents are the only workers (the Codex lane retired on 17 October 2026). Ruling dq (13 Nov) names what project threads and the coordinator themselves run on; these pins name the agents a thread starts. Name the actual model and effort in the receipt. A substitution blocks only a review or gate verdict that ran below its pinned tier; any other substitution is a note.
12. **Evidence.** Save disposable evidence under `artifacts/local/`; preserve historical evidence and owner changes. Report the checked version and the method. Automated play does not establish human feel or physical hardware support.
13. **Use locked dependencies and free local tools.** The go-ahead list below covers what changes what Andrew pays for or ships.

## Steps that need no approval

Act, then report. Andrew's standing approval covers these (27 October, widened 9 November):

- Retry any call that is safe to repeat when it fails, times out or finds a tool busy: reads, searches, `git fetch`, pushes to your own branch, tests, `npm run sketch:fast`, gate shards, bot runs, band sweeps, Godot imports and builds. A retry is not a new attempt.
- Commit, push and open draft pull requests on your own branch; edit `src/`, `assets/`, `tools/`, `registry.d`, tests and docs there.
- The Gate (the local session, ruling ds) stacks gate-passed pull requests onto the stage, promotes the stage to main, cuts the next stage, and pushes `stage/*`, `cand/*` and `scratch/*` branches.
- Decide game mechanics and tuning taste within the rulings, and record each call as a one-line assumption Andrew can overturn.
- Write and update memory, library files, hand-offs and private artifacts; resolve finished threads.

**Get Andrew's go-ahead first for:** deleting anything (merged-branch deletes go to his prune script as a list with recovery SHAs; other candidates go in `housekeeping/pending-deletes.md` in the project's shared folder, `/mnt/project-files/`), a force-push or history rewrite, an edit to `sketches/core-loop/package.json`, a dependency upgrade, an engine migration, a paid service, a deployment, anything outside the repo, and anything in `~/.local/share/godot/app_userdata/core-loop` (his saves and settings). A housekeeping task is not that go-ahead. Once he approves one, it has its go-ahead. The PC runs Godot only with the scratch folder, and the PC safety check stays as it is.

## Reference

- **Skills.** `scrapkeep-verify-game`, `scrapkeep-verify-build` and `scrapkeep-verify-web` show a feature working in the running game, the packed Linux build or a browser page, and keep the proof. `scrapkeep-verify` names the checks for a change, `scrapkeep-lab` runs the headless Godot lab, `scrapkeep-blockout` builds mojulo blockout pieces, `plan-session` plans, `scrapkeep-task` runs an authorized heavy-lane card, and `reactive-model-loop` covers a fast model that decides inside a running system. The bodies live under `.agents/skills/`, linked into `.claude/skills`. [.agents/skills/README.md](.agents/skills/README.md) says when to add one, and `npm run check:skills` checks them.
- **Game work rides the light play lane**, ORCHESTRATOR's lane for the Godot sketch under `sketches/`. The per-pull-request checks are rule 4. Native checks come from the approved engineering handoff, not guessed commands.
- **Documentation and configuration work** uses scoped structure, link and behaviour checks. Do not run builds under a no-build scope.
- **The older heavy lane** (ORCHESTRATOR's card-and-board process, for work outside the sketch). [The project desk](docs/project/README.md) is its start page. `BIBLE.md` and accepted `adr/` records own game and production direction, `BACKLOG.md` owns task definitions, `TRACKING.md` owns heavy-lane execution and questions, and `ORCHESTRATOR.md` owns assignment, isolation, review and integration. A proposed sprint or a ready card is not authorization to start it. Update the relevant ADR when a durable decision changes. In a local coordinator session that runs writer agents, each writer gets its own worktree with a verified base, and the coordinator alone admits changes and writes the canonical records; follow ORCHESTRATOR's scoped prose-staging exception.
- **The browser proofs.** `/` and `/orchard.html` are preserved proofs, not the current direction; keep them separate until consolidation is approved. Their tests do not qualify the native game. For a change to them, run `npm run verify` and the browser checks in CONTRIBUTING. Orchard combat state stays in `src/orchard/simulation.js`, rendering in `scene.js`, procedural models in `models.js`, and input and UI in `main.js`; read the lightning integration contract before you change an interface. Damage and telegraphs consume the same committed geometry.
- A project note creates no reminder, scheduled work or persistent memory.
