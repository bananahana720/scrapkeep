## 1. Instrument design

- **Leading wording inflates a headline claim by construction.** decide.mjs's prompt said "scrap has no use other than buying caches" and every cache was framed as ~1s; the retained sweep artifact itself contradicted the "price does nothing" headline (6/15 by the script's own rule, not 4/15; a tier-1-vs-tier-2-5 split under threat). audit/README.md:11-16 (findings 1-2), plan.md:47 (A1). Portable: any instrument whose prompt states a valuation and whose confound (tier/price/time/scrap all move together) can't be isolated will read out whatever the prompt asserts, dressed as a state-driven result.
- **Two near-identical question phrasings (q1 "single best intent" vs q2 "single intent," no "best/worth/should/costs you") measurably change behavior when the underlying facts differ across arms** — JL-15.md N1: P(take_cache) 0.74/0.69 under q1 vs 0.27/0.26 under neutral c1, later shown (JL-18/EV-0526) to be mostly an information gap, not framing, once c2 put the same facts (cost, stopping time, buff permanence, "scrap's sole use") into both arms' option text. reviews/JL-15.md:14, reviews/JL-18.md:14 (N1), EV-0526. Portable rule: a wording-neutrality control is invalid unless every decision-bearing fact is present in both arms' option text, not just the "intent" framing.
- **Information parity is necessary but not sufficient — check it explicitly, per fact.** JL-18's residual gap (q2-neutral still omitted "tier raises enemy health/spawn rate" that the current wording stated) produced a smaller but real remaining shift (0.24/0.38 vs 0.10/0.19). reviews/JL-18.md:14 (N1). Portable.
- **Controls that exist only in prose are not controls.** "Run sweep.mjs and any change to the questions has to clear the control first" had no corresponding code path; the cited pass/fail numbers (0.18 vs 0.81 → 0.62) had no artifact and were unreproducible. audit/README.md:15 (finding 3), :108 (A11). Portable, general engineering lesson but sharpened for judgement layers: a described control must be an executable, retained, live-run artifact or it is not evidence.
- **A negative control / adversarial set is worthless once the same person who wrote the prompt can also relabel cases after seeing output.** One case (`adv-full-hp-clock-burning`) was relabelled in the same commit that changed the prompt, flipping 37/41→39/41 and 3/4→4/4 adversarial. audit/README.md:16 (finding 4), :78-89 (label-edit history). Portable: single-session same-author label edits invalidate an adversarial/blind claim; require a blind, separately-authored corpus (see §2).
- **Per-option yes/no (Preference Nouls) vs single Choice measure different things and fail differently.** JL-18c design e sent one Noul per option (with full rules preamble) instead of one Choice over all options. Both methods failed the free-cache dominance control in the end, but for different reasons: Choice suffered position effects (range 0.147 vs 0.1 line) and framing; Preference Nouls had *no* position effect (ranges 0.007-0.018) and correctly top-rated take_cache in 18/18 calls, but failed only the pre-registered 0.2-margin-over-best-alternative rule (actual gap 0.10-0.14) because the competing "push_objective" option still scored a high Noul (~0.57) on its own. experiments/jl18c/RESULTS.md:9-18, :157-186. Portable: per-option Nouls remove position bias but replace "does X win" with "is X acceptable," which needs its own margin/ranking rule — that rule choice, not the model, decided the park in JL-18c's e-free-cache cell.
- **Position/order effects were measured directly, not assumed, and their shape differed by design and even flipped direction between JL-18 and JL-18c.** JL-18 review found a *last-position* boost (6 of 6 pairs moved the same way, 0.09-0.35 vs 0.03-0.06 same-position noise) — reviews/JL-18.md § 6. JL-18c's own run instead found a *first-position depression* in every flagged Choice cell (a-free-cache 0.39, c-no-objective 0.697, d-free-heal 0.617, f-free-cache 0.392 — each the lowest of its 3 positions). experiments/jl18c/RESULTS.md:43, per-cell tables :74-229. Method: run every permutation (2 options → both orders; 3 options → all six permutations), 3 repeats per order, report per-position mean/min/max/SD plus overall mean/min/pooled-SD, and require every order to pass independently (not the average). experiments/jl18c/PREREGISTRATION.md § "Designs," "Lines and definitions." Portable and important: position-effect direction is not a stable prior across even similar instruments/runs from the same day — always measure it in the run being judged, never assume "last wins" or "first wins" from a prior experiment.
- **Framing via a named objective/state field, not just wording, moved a Choice result by +0.303 (line 0.1) and was sufficient by itself to flip the free-cache verdict** (0.478 → 0.781, passing 6/6 orders) — removing `objective` from state, option id and option text. experiments/jl18c/RESULTS.md:32,40. This is Scrapkeep-specific in its content (the `objective: reach_exit` field) but the general lesson — that *naming a goal state adjacent to the option under test* biases a Choice toward the option that serves that goal — is portable.
- **Confidence floors need more than one calibration point, and they silently discard the raw signal.** `CONFIDENCE_FLOOR = 0.05` was "tuned against the corpus" on one sub-floor case (kicker-has-speed, confidence 0.02 vs next-lowest 0.25); decide.mjs:163-168 (per reviews/JL-15.md:22) replaces a sub-floor choice with `push_objective` and score.mjs discarded `rawIntent`, so "the model has no opinion" and "the model was overridden" were indistinguishable until JL-03 added `rawIntent`/`lowConfidence` fields (reviews/JL-03.md item 5, audit A6/A13). Now `CONFIDENCE_FLOOR` is documented as provisional in code: decide.mjs:21-23. Portable: any confidence floor / abstention threshold must retain the pre-floor raw output, or you cannot tell "correctly declined" from "silently overridden."
- **Gate preconditions (which options are even offered) are part of the instrument and need explicit test coverage**, not just the decision logic: audit A14 flagged `start_exit` precondition, the all-gated fallback, and the floor path as untested; JL-03 review confirmed these were added (reviews/JL-03.md item 6, DoD 6). Also: the option gate silently drops offers a Jev call never sees — a lethal-option control where the ram isn't offered is correctly scored as a control failure rather than a free pass (reviews/JL-15.md item 2, preflight.mjs:117-121 per that review).
- **GATE_VERSION is a manual constant, decoupled from what actually changes the option set (PRECONDITION, INTENTS fallback wording).** decide.mjs:25-26; reviews/JL-03.md N2-N3 note it must be bumped by hand and isn't. Portable: version/epoch identifiers for a decision instrument need either (a) a hash derived from every input that changes behavior, or (b) discipline/tests forcing a manual bump — a constant alone silently under-versions.
- **GATE_VERSION / instrument identity (epoch) covers questions_sha + model alias + confidence_floor + gate_version, but originally used the *floating* model alias `"jev-latest"` rather than the resolved model** (`jev-1.13.0`), so a passed epoch could silently cover a model that never ran the controls if TypeSafe moved the alias underneath it. decide.mjs:19-20,56-63; flagged at reviews/JL-15.md N5, fixed at JL-18b DoD 3 (`resolved_models` now stored, preflight.mjs per reviews/JL-18b.md item 3). Portable and important: pin the *resolved* model identity into any cache/epoch key that claims to bound "what was tested," not the alias you requested.
- **A dominance/threshold control must be forbidden from ever reading the cache**, and its pass condition needs an explicit probability line derived from measured noise, not a guessed constant. plan.md architecture § "Preflight controls" (free-cache P≥0.6, lethal-option P≤0.2, wording-swap same choice both ways, every control also reversed); JL-15 review confirmed `runControls` never passes a cache parameter to `decide()` (reviews/JL-15.md item 7). The 0.15 max-shift line for wording-swap was originally derived from n=1 pair of one wording's order-noise (reviews/JL-18.md N3) and shown by the very next run to be too low (same-wording order movement in that run ranged 0.09-0.35) — carried forward into JL-18c as "derive the noise line from the run being judged": `max(0.1, 3× pooled within-order SD)`. experiments/jl18c/PREREGISTRATION.md § "Lines and definitions." Portable: a threshold/margin constant copied from a prior run's noise is provisional at best and should be re-derived in-run wherever possible.
- **Confidence floors / gate preconditions and the "same choice both orders" control were shown to be insensitive at exactly the case that matters**: `preflight.mjs:214` returns before any noise check when both orders happen to agree, so a control can "pass" while still hiding a real wording effect if the effect wasn't large enough to flip the choice (reviews/JL-18.md N2, the swap controls "passed" a 0.28 and 0.17 shift under the one-sided same-choice rule, and would have failed a symmetric 0.15 line). Portable: a same-choice-only pass rule is blind to magnitude; pair it with a max-shift line, not either alone.

## 2. Evaluation discipline

- **Blind corpus construction rules, as built (JL-04):** a separate labeller agent whose FORBIDDEN list includes decide.mjs, the README, all Jev output and the authored corpus; inputs restricted to sketch READMEs, tuning.gd, and the Bible; every case records `{labeller, date, inputs_seen, prompt_epoch}`; blind results reach the prompt author only as aggregates; a case the author sees is "burned" and moves to the authored (non-gating) set; only blind scores gate. plan.md:82-87; enforced/reviewed reviews/JL-04-A1.md through -A3.md (labellers verified isolated, PROVENANCE.md audited for disclosed vs forbidden inputs). Portable, and directly reusable for any judge/labeller-model setup.
- **Blindness is fragile to reuse and to self-labelling.** JL-19's "blind" triage set was labelled by the same person/writer who also wrote the prompt and authored corpus — reviews/JL-19.md finding 2 explicitly flags this as exactly the audit-A2 weakness, and notes that once the writer saw per-case blind misses in the score report, the set becomes burned for any future wording change under the plan's own convention. Portable, cautionary: a corpus is "blind" only relative to a specific boundary (prompt author vs model), and that boundary must be checked per new use, not assumed inherited.
- **Text-only baselines are mandatory and were run repeatedly, with escalating rigor.** JL-04-A3 reviewer hand-built a rule-based picker and beat the writer's own reported baseline (71% vs writer's claimed 61%, chance 48%) — reviews/JL-04-A3.md N2 — attributing most of the "edge" to game-rule priors and corpus composition, not to the labels being guessable. A text-only baseline scanner (`text-only-baseline.mjs`) is cited as missing patterns (only single-token checks) that a human reviewer caught by hand (compass-verb split, reviews/JL-04-A3.md N1). Portable: automate the baseline scanner but also spot-check by hand — automated neutrality/baseline scans (`neutrality-scan.mjs`, `why-wording.out`) repeatedly missed things a human reviewer found (e.g., "marked spot" telegraph wording in JL-04-A2 F1, which a text-only rule scored 5/5 on).
- **Neutrality review went through two explicit FAIL/re-review cycles before passing** (JL-04-A2 FAIL on F1 "telegraph wording still decides 5 cases from text alone" despite meeting the literal DoD; JL-04-A3 PASS+NOTES after the fix, with residual wording cues flagged as "portable only via cross-case statistics, not single-case", judged non-blocking). EV-0490, EV-0496, reviews/JL-04-A2.md, -A3.md. Portable process lesson: neutrality has to be checked against "would a rule that reads text only, ignoring state, get this right" — not just "does the wording sound neutral."
- **Pre-registration and hash-pinning of inputs before any live call, with a runner that refuses to start on a hash mismatch.** JL-18c: PREREGISTRATION.md pins sha256 of states.json, questions.json, design.json, run.mjs; `--live` refuses to start unless every hash matches; the change record explicitly logs a pre-Phase-B change (dropping free-heal from verdict cells) with who requested it and why, before any call. experiments/jl18c/PREREGISTRATION.md:202-210, "Change record" :170. Provenance is captured both before and after the run (git HEAD, `git status --porcelain`, sha256 of the prereg file), and the run is enforced as run-once ("Phase B ... runs once, and changes nothing here", "A crash mid-run counts as BLOCKED"). experiments/jl18c/RESULTS.md:46-56. Portable and one of the strongest patterns in this record for any high-stakes single-shot model evaluation.
- **"Post-hoc selection disclosure":** JL-18c's results explicitly separate "pre-registered readings that fired" (a fixed table, rows never added after the fact — "The Phase B report states which rows fired and cites the numbers. It does not add rows.", PREREGISTRATION.md:154) from "observations that are not pre-registered rows, reported for the reviewer" (RESULTS.md:42-44, the position-direction flip). Portable: keep a hard line between confirmatory (pre-registered) and exploratory findings in the same report, and label which is which.
- **Retraction is append-only and explicit, never a silent edit.** Because TRACKING is append-only, EV-0485 is a compensating event that retracts specific numeric claims (audit finding by finding) rather than rewriting EV-0483; EV-0492 similarly corrects fabricated timestamps in EV-0486–EV-0491 via a new event, not an edit. audit/README.md § "Verdict on retraction"; EV-0485; EV-0492. Portable pattern for any append-only ledger of model-assisted claims.
- **"Measured vs simulated" qualifiers were enforced strictly.** Numbers computed from arithmetic ("62 s = 8 × 7.7 s," "~260 s serial") were retagged "U" (unverified/computed) in the claims ledger even though internally consistent, distinguished from artifact-backed "V" claims. audit/README.md § claims ledger (e.g. commit 9c067de rows), A5. Portable: a computed number dressed as a measurement is a specific, recurring failure mode this project tracks explicitly with a V/U/R taxonomy.
- **Qualifiers when the labeller also wrote the prompt / question set are required in the review output itself**, not just as a caveat buried in a doc: reviews/JL-04-A1.md and -A2.md open with "It cites case ids ... whoever authors a question set must not read it," and JL-18's own reviewer explicitly avoided opening the blind corpus, PROVENANCE, or any JL-04 review to preserve isolation (reviews/JL-18.md:5, "I did not open the blind corpus..."). Portable operational discipline: state what you deliberately did NOT read, not just what you read.
- **Comparison against a free/cheap rule as a standing check**, run more than once at increasing rigor: JL-04-A3's rule-based baseline (71%), and JL-19's fallback deterministic rule (`real_regression` always, conservative-by-construction) used as the non-Jev floor for triage (reviews/JL-19.md "Fallback is conservative on every path"). Portable.

## 3. Runtime engineering

- **Verdict cache key = `sha256({protocol, questions_sha, model, confidence_floor, gate_version, state, options})`** — plan.md:111, i.e. keyed on the *requested* protocol/instrument identity, not necessarily the resolved model (see §1's alias-vs-resolved gap, later closed by storing `resolved_models` in the epoch record, JL-18b DoD 3). Portable pattern with the portable caveat: prefer the resolved model in any identity that gates trust.
- **Replay makes zero API calls; a cache miss during replay is an error, not a silent live call** — plan.md:112, confirmed in JL-18b review ("a replay makes no call ... a two-model cache voids it"). Its residual risk: a cache entry with a *null* resolved model (from an older/hand-edited cache) leaves the replay anchor null, so *any* later verdict passes both checks — reviews/JL-18b.md N2, recommends treating a null model as a mismatch. Portable and worth flagging generally: replay/cache-integrity checks must treat "field absent" as a distinct, suspicious case, not as "no constraint."
- **Redaction runs before clipping, before hashing, and before the cache key is built** — verified ordering, reviews/JL-19.md finding 3 closing paragraph and criteria section (triage.mjs, `:191` clip, `:330` hash, `:336` cache key). But redaction coverage had real gaps found by the reviewer, not assumed complete: missing `i` flag on a Bearer-token regex (lowercase "bearer" survives), JSON-quoted secrets (`"api_key": "..."`) not matching a prefix pattern, home-path usernames surviving when joined by a colon to another path, and an API key read from the local `.env` file not being redacted in `score` mode because it enters as `call`, outside the literal-secret list. reviews/JL-19.md finding 3, items at `:127,:136,:149,:173-176,:319-323`. Portable and important: redact-before-anything-leaves is the right design, but coverage must be tested against adversarial formats (case, quoting, path-joining), not just the happy-path secret shapes.
- **Fallbacks are never cached and are conservative on every failure path** — no key, HTTP error, timeout (8s), malformed reply, off-menu choice: all return the same safe default (`real_regression`, not rerun-safe for JL-19's triage) and none is cached (reviews/JL-19.md "Fallback is conservative on every path," test citations `:215-274`). But **a fallback can still pass a control if the control-pass check doesn't verify the answer's source** — `scoreCases` counted `control.passed` without checking `source`, so 26 rule-fallback answers (from a CallCap refusal cascade) counted as a passing control in one probe run; the final scored run happened to have 0 fallbacks so the reported number held, but the gap is real (reviews/JL-19.md finding 4). Portable and a genuinely reusable lesson: a control/gate check must assert the answer came from the live decider, not merely that it matches the expected label — a deterministic fallback can accidentally "pass" a control by luck or by construction.
- **Timeouts, call caps and epochs:** 8s call timeout (JL-19 triage); live-call caps set per batch and enforced with CallCap refusals that short-circuit before sending a request (JL-19 rows 3-28 "26 CallCap refusals... No request was sent for them" — reviews/JL-19.md finding 1); global runaway-guard token cap authorized program-wide at EV-0484 ("cost not a constraint" but "each batch carries a call cap set in JL-11"); JL-20's cross-run call cap undercounts failed calls because failures throw before the log line that increments the counter is written (reviews/JL-20.md finding 5) — a portable bug pattern: any call-cap accounting that increments only on a logged success line will silently under-count against a cross-run/cross-session cap.
- **Token field names, never summed across fields, and null vs zero matters.** Every review explicitly separates `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` and flags when cache fields were *absent* (recorded correctly as null post-fix) vs an earlier code version that printed 0 for an absent field (reviews/JL-15.md N3, corrected at EV-0520: "the cache-token fields were absent from every call's usage; the retained totals print 0 because the run was made at c078854, and 7f5f44f totals an unreported field as null; the run was not repeated"). This directly instantiates the user's stated home-preference rule (never sum priced fields, treat absent vs zero as different facts) inside the project's own runtime engineering.
- **Latency was measured, not assumed:** JL-18c reports per-call latency range (81-448 ms) alongside the retained run record; earlier retracted claims ("round trip ~286 ms") were shown inconsistent across three sources (decide.mjs comment 223ms, README ~280ms, one committed number) and corrected to the actual retained-run median (294ms) — audit/README.md claim-ledger row, EV-0485. Portable: any latency claim needs to cite which retained artifact it's computed from, and stale copy (a README table not regenerated after a prompt change) is a recurring failure this project caught twice (audit A15, reviews/JL-15.md, similar pattern).
- **Epochs and re-pinning:** an epoch = one instrument identity hash; a rerun *replaces* the earlier record for that key by design (preflight.mjs comment "a rerun replaces the earlier record"), but this was found unsafe when *every* call in a rerun errors (e.g., a 503 storm) — an all-error run would overwrite a previously-passed epoch record with a failed one (reviews/JL-15.md N6). Fixed at JL-18b DoD 3: "All-error run writes `<key>.error.json` beside an existing record and never replaces it ... a partial-error run does replace." reviews/JL-18b.md item 3. Portable and a nicely specific lesson: "last write wins" epoch/cache semantics need a carve-out for "the whole batch was infrastructure failure," or a transient outage can erase a previously-earned pass.

Qualifier: JL-18c's own analysis attributes the free-cache failure to position (+0.147 range vs 0.1 line) and to framing/naming the objective (+0.303 lift, and *sufficient by itself* — removing the objective flipped the cell from fail to pass 6/6) rather than to reading failure (33/33 comprehension items correct) or to priming from adjacent danger/greedy questions (+0.0095 lift, not indicated).

- **Failure triage (JL-19): model helped, with caveats.** Authored score 70/78, blind score 65/71, 0 severe misses, 0 fallbacks in the final run (reviews/JL-19.md DoD 2). An injected `assert(false)` control correctly returned `real_regression` (plan.md:208 control spec). Caveats: the blind set is not blind to the prompt author (finding 2, above); a result-triggered mid-run prompt change contaminated the authored (non-gating) score but not the blind score (finding 1); rerun-safety labels were internally inconsistent across similarly-persistent infra failure types (quota/ENOSPC labelled safe, EACCES/missing-tool labelled unsafe, finding 7).
- **Watch/test ordering (JL-23) and coverage gap (JL-24):** named in plan.md's card table (JL-23 "reorders only; it never skips," control = "a test that imports the changed file must outrank one that doesn't"; JL-24 control = "a file with no test at all must be flagged") but I found no review artifact for JL-23 or JL-24 among the retained files listed — they do not appear in the reviews/ directory glob or in the TRACKING rows read. **Open question** (see below): whether JL-23/JL-24 ran and what their live numbers were is not evidenced in the sources I was given.
- **Verdict tagging (JL-20): passed its narrow contract, with an explicit scope caveat the reviewer says is under-communicated.** 14/14 tag agreement (hand labels vs Jev per-tag Nouls, forward+exact-reverse order, max order gap 0.01), model jev-1.13.0 (reviews/JL-20.md DoD 2, "The two answers are averaged... mean order gap 0.01"). Reviewer's finding 1 explicitly caveats: this is agreement on *easy* cases only — Nouls ranged 0.02-0.10 or 0.97-0.99, "not calibration" — and finding 3 notes the tag vocabulary "echoes the control quotes" (lexically close to the two labelled entries), which "strengthens finding 1." By card design the tagger can only confirm existing hand labels and never fills an unlabelled entry (finding 2) — a scaling limit for `agent_agreement`, not a defect.
- **Program-level Jev roles kept off the gate path throughout:** "Nothing on the gate path waits on Jev. gate and npm run verify never depend on it." plan.md:203, verified per-card (e.g., reviews/JL-19.md finding 6 and reviews/JL-20.md finding 4 both check that no gate-path import reaches the Jev-calling module, though both note the isolation test only checks direct imports, not transitive ones — a repeated, explicitly-flagged coverage gap).
