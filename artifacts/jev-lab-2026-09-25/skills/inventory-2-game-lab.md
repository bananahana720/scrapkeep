# 1. Godot↔Node file protocol

- **Rule:** Lockstep runs over files in one `<io>` dir per trial, never sockets, per TADR-005. Why: architectural decision, not discovered defect. Cite: `tools/jev-player/protocol/PROTOCOL.md:1-3`. Portable (any engine-in-the-loop design facing a no-sockets ADR).
- **Rule:** Every file has exactly one writer; write `<name>.tmp` then rename; readers ignore `*.tmp`. Why: avoids partial-read races without locks. Cite: `PROTOCOL.md:7-8`. Portable.
- **Rule:** Tick schedule is D=snapshot_every=90, k=hold_ticks=26 (must have k<D); Godot snapshots at t=seq×D, keeps flying the held intent to t+k, blocks in `_physics_process` via `OS.delay_msec` (never `tree.paused`, which would pause Jolt) until intent arrives, applies exactly at t+k. Why: k<D guarantees `state-(seq+1).held` is always `intent-seq`; blocking-not-pausing avoids Jolt's pause/unpause semantics. Cite: `PROTOCOL.md:98-107`; header rationale in `sketches/ball-lab/src/jev/jev_run.gd:11-16`. Scrapkeep-specific (Jolt physics detail), pattern (blocking a subprocess instead of engine-pause) is portable.
- **Rule:** `trace_hash` = SHA-256 over the raw bytes of `events.ndjson` only; `sim` (Godot's pos/vel view) is unchecked and never hashed or shown to the arm. Why: keeps determinism checks and cache keys clean of any wall-clock/debug noise. Cite: `PROTOCOL.md:45,80,158`; confirmed reproducible by JL-05 review (`artifacts/jev-lab-2026-09-25/reviews/JL-05.md`, TRACKING EV-0499 line 800) and JL-17's real-process bridge test under 3 responder-delay patterns (EV-0542, line 843).
- **Rule:** Schemas are closed — unknown fields invalid except inside `sim`/`meta`; own-string-key lookups only (prototype-chain names like `constructor`, `__proto__`, `toString`, or arrays like `["takeoff"]` must be rejected, never silently coerced). Why (bug found): JL-09's Godot port discovered Node's `protocol.mjs` accepted event kind `constructor` and arm `["ram_target"]` through JS prototype lookup/array coercion, and threw (rather than returning a validation error) on arm `.toString` — the same latent pattern existed in `decide.mjs`'s `PRECONDITION` lookup. Fixed in JL-05c with own-string-key guards; base Node wrongly accepted 5 / threw on 4 of 27 new fixtures before the fix. Cite: TRACKING EV-0513 (line 814), EV-0524 (line 825); `PROTOCOL.md:12`. Portable (classic JS prototype-pollution-adjacent parsing bug — applies to any Node validator keyed on untrusted strings).
- **Rule:** Whole-number fields must be exact integers; "steps of 0.1" fields allow ≤1e-9 slack (float grid tolerance), not a second coarser grid. Why (bug found): Node checked jev whole numbers exactly where PROTOCOL.md allowed 1e-9 slack — a spec/impl mismatch JL-09 surfaced by independently re-implementing the Godot side from the doc alone. Cite: TRACKING EV-0513 (line 814); `PROTOCOL.md:176`. Scrapkeep-specific numbers, portable practice (port from spec text, not from the reference implementation, to catch doc/code drift).
- **Rule:** Fixtures are a single canonical source (`tools/jev-player/protocol/fixtures/`) byte-copied into the Godot project (`sketches/ball-lab/src/jev/fixtures/`) with an automated drift test comparing them, so both validators are exercised against the same corpus. Why: prevents the two independent implementations (Node, GDScript) from silently diverging. Cite: `PROTOCOL.md:186`; TRACKING EV-0499 carry-forward (line 800), EV-0513 (line 814, "byte-identical" confirmed). Portable pattern for any dual-implementation protocol.
- **Rule:** Validators on both sides, built independently from the same written spec (not from each other's code), then reconciled — this is what found the prototype-lookup, whole-number-tolerance and non-empty-string gaps. Why/evidence: explicitly, JL-09's writer built `jev_io.gd` from `PROTOCOL.md` alone and found 3 Node validator defects plus 3 spec gaps (gate rules stated only in `decide.mjs`, not in the doc; non-empty-string rule unstated). Cite: TRACKING EV-0513 (line 814), EV-0517 (line 818: reviewer confirmed "the Godot gate port matches decide.mjs rule by rule" and same prototype-lookup pattern latent in `decide.mjs`'s own PRECONDITION lookup). Portable: independent re-derivation from a shared spec is a strong review technique, distinct from code review.
- **Rule:** Outcome-precedence is a total order, not first-detected: watchdog stall > Node-side file rejection (`invalid`) > `done.json`/`error.json` (else `crash`); a Node rejection outranks a later engine crash. Why: needed once multiple failure paths could race (e.g. Godot exits after Node already rejected a bad state file). Cite: `PROTOCOL.md:129`; correction routed via JL-05c N2 (TRACKING EV-0524, line 825). Portable.
- **Rule:** The verdict-cache key is `sha256(canonicalJson({protocol, questions_sha, model, confidence_floor, gate_version, state, options}))`, computed by Node only (Godot never computes/checks it); `gate_version` bump required whenever precondition-gate rules or the all-gated fallback change, checked by a cross-file agreement test across `decide.mjs`, `jev_io.gd` and `PROTOCOL.md`. Cite: `PROTOCOL.md:154,158`. Portable caching pattern for any LLM-decision cache needing exact provenance.
- **Rule:** `abort.json` reasons are a closed enum (`interrupted`, `arm_error`, `replay_miss`); an unreported field from a live API (e.g. missing cache-token counts) must be recorded as `null`, never defaulted to `0`. Why (bug found twice): EV-0521 discovered the real Jev API returns exactly `{answers, model, usage:{input_tokens,output_tokens}}` — no cache fields — settling an open question from EV-0489; a later `record.mjs` regression recorded unreported fields as 0, flagged as carried-forward defect F2 in EV-0523 (line 824). Cite: TRACKING EV-0521 (line 822), EV-0523 (line 824). Portable: never let "field absent" collapse into "value zero" in cost/usage accounting.

# 2. Determinism

- **Rule:** Kinematic mode is fully reproducible; rigid (Jolt) mode is not — treat any rigid divergence as stochastic, not a protocol bug, by design. Cite: `PROTOCOL.md:178-182`.
- **Evidence, repeat-pair rate:** Kinematic 360/360 identical trace hashes across three repeat sweeps; rigid divergence measured at roughly 1 flip in 20 trials (2/20 and 1/20 seen across groups), and critically **the divergence can flip the scenario outcome**, not just jitter positions — same seed/spawn/D/k gave `timeout` in one run and `success` at tick 3544 in a repeat (hashes `7c639f71…` vs `2faf1b92…`). Cite: JL-21 review F2, `artifacts/jev-lab-2026-09-25/reviews/JL-21.md:15`; TRACKING EV-0546 (line 847, "rigid trials diverge in about 1 of 20 and can flip the outcome"). Scrapkeep-specific (Jolt), but the finding-pattern (physics-engine nondeterminism silently flipping pass/fail) is portable to any headless gameplay-gate design.
- **Rule/gate consequence:** because of this, gates must split by mode — kinematic gets exact trace-hash/replay equality (golden master), rigid gets distributional comparison only, n≥20 each side, with an explicit nondeterminism floor (~0.05, i.e. ~1-in-20). Cite: JL-25 candidate description, TRACKING EV-0550 (line 851); qualified by JL-25 review F1/F2 — the rigid gate as shipped states "distributions" but **compares no rate at all** (no batch metric in `RATES`; the rigid pin itself has 0/20 success so `reachability` never fires), i.e. the distributional claim overstated what the code does. Cite: `artifacts/jev-lab-2026-09-25/reviews/JL-25.md:9-13` (F1, F2). This is a genuine unresolved gap, not fixed within the program (see Open Questions).
- **Sensitivity control:** a dedicated determinism test perturbs one intent answer or the D/k schedule (k=54 vs 26) and confirms the hash changes while pre-perturbation events stay byte-identical — proving the hash is neither always-equal nor spuriously order-independent. Cite: TRACKING EV-0546 (line 847); JL-21 review §1.4, `reviews/JL-21.md:34`. Portable technique for validating any content hash used as a regression oracle.
- **What flips outcomes / per-stage difference:** ball-lab's only RNG source is visual camera jitter (unhashed); stages hard-code seeds overridden by `seed_override`; the lab ports (Cable Bench, Spillway Drop) added `seed_override := -1` to reuse each stage's original hand-picked seeds when not overridden. Cite: `PROTOCOL.md:181`; plan.md:131; JL-26 review §1, `reviews/JL-26.md:55-57` (confirms `_seed_for` returns exactly the archived literal seeds under -1).

# 3. Scenarios and arms

- **Rule/bug found:** a scripted rule-ladder baseline with no memory and no "threat neutralised" condition can score *below* the random floor on objective scenarios, because it loops forever attacking a threat the game never removes. Why: ball-lab's scripted ladder picks `stomp_target` for any dummy within 12 m with no cooldown, and dummies chase endlessly with no HP/leash, so once a dummy enters range the ladder never returns to `push_objective` — 0/20 success vs random's non-zero rate on the same scenario. Cite: TRACKING EV-0546 (line 847, "the scripted arm scores below random... scripted never pushes the objective"); JL-21 review F1, `reviews/JL-21.md:9-13` (traces the exact mechanism in `arms.mjs:68-73` and `enemy.gd:48-54`, with a concrete 20/20-timeout trial). **Fix chosen:** hide a knocked threat from the exported *state* (not the ladder) once this trial has knocked it, applied identically to every arm — the minimal in-boundary fix that "mirrors the game" without tuning the rule itself. Cite: JL-21 review F1 recommendation, EV-0546. Portable lesson: a hand-written baseline policy needs an explicit termination/memory condition or it silently becomes a worse-than-random floor, and the fix belongs in the shared world-state, not in the policy, to avoid overfitting one arm.
- **Threat rules per stage differ and were the subject of an explicit coordinator ruling ("stage-threat-rule 2"):** ball-lab dummies cannot die, so "knocked" ≈ "out of play" there; but Cable Bench and Spillway Drop enemies **survive a knock and keep chasing** — a knocked/damaged-but-alive foe must stay in the exported threat list. The ruling: a threat leaves the exported state only when the game has permanently taken it out of play (dead or freed), for every arm alike. Why this mattered: applying ball-lab's "knocked = gone" rule to Cable Bench let a 260-HP miniboss (a 26-HP-per-stomp) vanish from state after one hit while still alive and lethal, confounding two of three Cable Bench scenarios (`forge-charge`, `stage-run` both 0/20 across every arm/mode). Cite: TRACKING EV-0550 (line 851, ruling); JL-26 `jev_state.gd:15-19` header; JL-26 review N1, `reviews/JL-26.md:18-23` (names the confound and its likely cause as inference, labeled "the coordinator should decide... that would be a new instrument epoch" — i.e. flagged as unresolved even after the fix). Portable: a state-export rule encoding "is this a threat" must be validated per-mechanic (can it die? can it be permanently removed?), not copied across stages/games.
- **Spawn jitter for real choices, not forced snapshots:** a scenario with `jitter_m>0` places the ball at a seeded point in a disc around nominal spawn; trial *i* gets the same jittered point on every arm so arms are paired, not just seed-matched — otherwise a deterministic arm's 20 "trials" are really 1 trial repeated 20 times. Cite: `sketches/ball-lab/src/jev/scenarios.gd:13-16`; JL-21 review §2.5, `reviews/JL-21.md:41`. Portable statistics-of-simulation lesson.
- **Time limits from scripted p90, with a defect (censoring):** the rule is `max(initial, 2×scripted-p90-over-20-trials)`, but because of the scripted-ladder defect above, scripted p90 was *censored* (right at or past the timeout) on every one of the four choice scenarios, so no scenario's limit ever actually moved off its initial value — the review explicitly separates "rule applied correctly" from "input was invalid," recording DoD as inconclusive rather than met/failed. Cite: JL-21 review F6, `reviews/JL-21.md:23`; TRACKING EV-0546 (line 847, "recorded as inconclusive... limits provisional"). Portable: an automatic calibration rule can pass its own procedural check while its statistical premise (an uncensored p90) silently fails — check the input distribution's shape, not just that the formula ran.
- **Speed gates the policy cannot reach — a semantics bug, not a tuning problem:** `hit_kicker` was offered whenever within 60 m with `requires_speed_ms=17.2`, but the precondition gate checks the ball's *current* speed at decision time, not the run-up speed it will reach by the time it hits the kicker — and the agent's own run-up *starts* below 3 m/s, so the option almost never survives the gate (7 of 40 trials on one arm, 0/40 on the other; the whole `bench-climb` scenario went 0/20 for every arm/mode as a result). Fix used in the lab ports: gate on reachable run-up geometry (e.g. "is the kicker's run-up within range on the ball's current bench"), not on instantaneous speed. Cite: JL-21 review F4, `reviews/JL-21.md:19`; JL-26's `jev_state.gd:22-25` header explicitly encodes the fix and cites "JL-21 review, F4." Portable: a precondition gate checking present state for a target reachable only via future action is a category error, distinct from needing a better speed constant.
- **Calibrating constants from physics-only sweeps, not gameplay trials:** `requires_speed_ms` (17.2 m/s) and the kicker "lip" location were derived from a dedicated physics probe (spawn just before the lip, launch at varying speeds, measure lip-crossing speed and whether the ball clears), separate from and prior to any scenario/arm trial. Cite: TRACKING EV-0546 (line 847); JL-21 review §2.4 method, `reviews/JL-21.md:40`. Portable: separate "what can the physics do" calibration from "how does the policy perform" measurement — conflating them makes a tuning result look like a policy result.

# 4. Records, gates and pins

- **Run record schema `scrapkeep-run/1`:** one exclusive directory per run, claimed by opening `run-owner.json` with `O_EXCL`-style `x` flag (pattern reused from `tools/agent-player/run.py:88-99`); `run.json` carries identity, provenance (git head/branch/dirty, source hashes at start and end — a start/end mismatch demotes the run to `inconclusive`), config, kpis/kris each as `{value,n,ci}`, findings with repro commands, and limits. Cite: plan.md:140-149; `scripts/lab/record.mjs:1-25`.
- **Gate exit codes are a 5-way enum, not pass/fail:** 0 pass, 1 red-KRI/conclusive regression, 2 usage error, 3 inconclusive (too few samples/stale baseline/dirty tree/blind set <20), 4 instrument invalid (failed control, new unqualified epoch, invalid record). Cite: plan.md:173-181; qualified live by JL-25's gate-qualification card, which drove real injected regressions through exits 1→0→4→4 (TRACKING EV-0550, line 851).
- **Bug found — a passing golden-master gate can't distinguish "changed" from "regressed":** the kinematic gate's exit 1 fires purely on trace-hash mismatch; an injected -10% `drive_accel` regression produced the *same* 14/20 success rate as the pin (no behavioral regression) yet still failed with exit 1 because all 20 hashes differ. Reviewer's finding: "`replay_repro` red" is a semantic stretch for a candidate at a different commit (that's not a "replay"), and the gate has *no* success-rate/outcome comparison at all in its `RATES` table — so exit 1 answers "did anything change" not "did it get worse." Recorded resolution: label a kinematic exit 1 as "behaviour differs from the pin," defer "worse" to the later comparison card (JL-28), and note a real outcome-rate comparison (Newcombe interval on success/n) is still a follow-up, not built. Cite: JL-25 review F1, `artifacts/jev-lab-2026-09-25/reviews/JL-25.md:9`; TRACKING EV-0550 (line 851, "a kinematic exit 1 means 'behaviour differs from the pin'... not 'worse', which is JL-28's question"). Portable, important: a golden-master (trace-equality) gate is a change detector, not a regression detector, unless paired with an explicit outcome-metric comparison — don't conflate the two in status reporting.
- **`andrew-anchor` pin — subject provenance gap found:** the anchor pin (the build Andrew actually played, exempt from the 7-day staleness rule) recorded git provenance for the *harness worktree*, not a verifiable digest of the actual exported sketch tree (`dc94b2c`) it claims to represent — "this is dc94b2c" rested on trusting an unmodified export script, with no tree-OID/hash of the subject itself. Fix applied: `--pin` gained `--subject-commit`/`--subject-path`, and `pin.json` gained a `subject` block naming commit, path and tree hash. Cite: JL-25 review F3, `reviews/JL-25.md:13`; TRACKING EV-0550-EV-0551 (lines 851-852, fix landed). Portable: a "ground truth" pin needs its own content-addressed identity, separate from the harness's git state, or its authority is unverifiable.
- **Epochs:** an epoch = the full instrument identity (question-set sha, resolved model, confidence floor, gate version); pinning an instrumented (jev-arm) run requires that instrument's epoch to have passed both live preflight controls and the blind corpus; a changed prompt or model starts a new epoch that is invalid until both re-pass (exit 4 in the meantime). Cite: plan.md:67-70,171; multiple live demonstrations — q1's epoch was retroactively invalid (EV-0485), q2's epoch stayed invalid all session after failing the free-cache control (EV-0526, EV-0529).
- **Dirty-tree gate on pins:** running the actual gate qualification (JL-25) found the gate's `dirty` flag only tracks the declared *source paths*, so an untracked file (e.g. a newly created pin directory) outside those paths goes unnoticed even while the run correctly reports `dirty:false`. Cite: JL-25 review F8 (observation), `reviews/JL-25.md:23`. Minor/portable caution: "dirty" checks are only as complete as their declared source-path list.
- **Re-runs at head, not at a dirty base:** the coordinator required, and used, a cheap re-run-at-clean-head check to validate whether calibration batches run on a dirty tree still reflect the code actually merged — since kinematic mode is deterministic, matching trace hashes between the dirty-tree run and a clean-head re-run proves the executed code path is unchanged, without re-running the full (expensive, ~16 min) batch set. Cite: TRACKING EV-0546 (line 847, "the scripted dummy-knock kinematic batch re-run at clean head 93799e9 matched the original batch trace hash for trace hash, 20 of 20"); this pattern is explicitly recommended by the JL-21 review as the cheap check before trusting dirty-tree calibration numbers (F5, `reviews/JL-21.md:21`). Portable, elegant: use a deterministic-mode hash-equality re-run as a cheap proxy for "was this dirty-tree evidence produced by the code that's actually being merged."
