### Configure Bash tool permissions with wildcards in JSON

Source: https://code.claude.com/docs/en/permissions

Defines permission rules using glob patterns to allow specific Bash commands while denying others like git push.

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)",
      "Bash(git * main)",
      "Bash(* --version)",
      "Bash(* --help *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}
```

### Configure Ask Permission Rules in settings.json

Source: https://code.claude.com/docs/en/settings-reference

Prompts for confirmation on matching tool calls even in permissive modes like acceptEdits or bypassPermissions. Denies matching calls automatically when running in dontAsk mode.

```json
{
  "permissions": {
    "ask": ["Bash(git push *)"]
  }
}
```

--------------------------------

### Configure Deny Permission Rules in settings.json

Source: https://code.claude.com/docs/en/settings-reference

Blocks tool executions and hides matching sensitive files from discovery, read, and edit tools across all modes. Deny rules apply to built-in file tools and recognized shell commands.

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(./config/credentials.json)",
      "Bash(curl *)"
    ]
  }
}
```

### Permission rule syntax > Wildcard patterns

Source: https://code.claude.com/docs/en/permissions

Bash permission rules support glob wildcard patterns with * to match command prefixes, suffixes, or arguments. The :* suffix functions as an equivalent trailing wildcard syntax (such as Bash(ls:*) matching the same commands as Bash(ls *)), but it is only recognized at the end of a pattern.

--------------------------------

### Glossary > P > Permission rule

Source: https://code.claude.com/docs/en/glossary

A permission rule is a fine-grained settings entry that allows, asks about, or denies tool invocations based on the tool name and argument pattern. Rules operate on top of the broader permission mode and are evaluated in the order of deny, then ask, then allow, with the first matching rule taking precedence.
