## Contract

### What this section fixes

It fixes six views with their entry, exit, focus and pause requirements; six display rules that bound what any view is allowed to show or decide; ten interface states with the published basis, required visible feedback and unavailable actions of each; fourteen focus, restoration and recapture requirements written so that navigation cannot cast; sixteen unresolved interface parameters, each carrying a source line or a question ID and no value; a transition walk over Bible Section 6; and sixteen review scenarios, one per view and one per state, each naming its visible feedback, its unavailable actions and the questions a reviewer must see exposed rather than answered.

It fixes no screen layout, no anchor position, no control geometry, no font or target size, no viewing distance, no display size, no controller device, binding or glyph, no inventory capacity, no equipment slot count, no respec price, no revival health value and no timing. Where the interface needs one of those, the requirement below names what must be true of it and routes the value to its question. It is not an implementation and nothing here has been rendered, navigated or measured.

### Vocabulary

**View** is a named region of the production interface with its own entry and exit, not a screen or a scene. **State** is a condition a view must express, rebuilt from published values each time it is shown, never stored (TH-07 PR-03 line 112; TH-04 AA-05 line 56). **Input class** labels what a player action is allowed to become, and is the load-bearing distinction in this section:

| Class | Meaning | May reach `submit_action` |
| --- | --- | --- |
| `navigation` | Moving interactive focus, opening or closing a view, or activating a control whose whole effect is navigation. | Never |
| `ui-request` | Activating a control that records a `UiRequest` Session later reads as a value (TH-01 IF-19 line 92). | Never |
| `control` | The pause, resume and capture work of the control drain (HF-04a O1 line 87 to HF-04a O4 line 90). | Never |
| `gameplay` | An action request routed into the encounter inbox at RL2 (TH-01 IF-14 line 87). | Yes, and only here |
| `display` | Presentation showing an existing published result (HF-04a F-PROCESS line 44). | Never |

A `gameplay` step exists only while the encounter is ticking at TH-01 RL2 line 36. No `navigation`, `ui-request`, `control` or `display` step reaches `submit_action` anywhere in this section, and the paper check under [Procedure performed](#procedure-performed) asserts it mechanically.

### Focus restoration, keyboard and controller navigation, and pointer recapture

Bible line 602 states the requirement: keyboard navigation, focus restoration and pointer recapture must avoid accidental casts. The engineering contract already supplies the mechanism; this section states what the interface must therefore do and what a reviewer must be able to check, and selects no binding, device or layout.

| ID | Requirement | Source |
| --- | --- | --- |
| FP-01 | Every transition out of gameplay into an interactive view performs the control drain in order: release held physical input, cancel prepared actions, then pause. The interactive view is shown only after that sequence completes, so the first frame the player can navigate is already a frame in which no gameplay input is held. | HF-04a line 92; HF-04a O1 line 87; HF-04a O2 line 88; HF-04a O3 line 89 |
| FP-02 | A focus or modal notification arriving mid-tick is latched and the sequence completes at the first non-reentrant control boundary, before another tick. The interface must not appear to open before that, because a half-opened view invites a navigation press while gameplay is still live. | HF-04a line 92 |
| FP-03 | Held state, previous-edge state and pending physical edges are cleared and the input-context generation advances, and each gameplay control is re-armed only after it is observed neutral in the new context. A key or button still held when the view opened cannot reappear as a fresh press on return. | HF-04a O1 line 87 |
| FP-04 | The pause, resume and capture action is consumed as UI input and produces no gameplay release edge. The control the player presses to leave or re-enter the interface is never also the control that fires. | HF-04a O1 line 87 |
| FP-05 | Pause alone is not accidental-cast protection. A bare internal pause does not cancel a prepared action, and any route that exposes pause to focus or menu navigation must use the full sequence. | FP-07 | Regaining window focus never resumes gameplay by itself. Returning to the window returns the player to a paused interface, and leaving it takes a deliberate `control` action. | HF-04a line 92 |
| FP-08 | A rejected pointer capture keeps the interface paused and exposes a retry, and that retry action cannot also become a shot. The interface must show the capture state plainly, because a player who cannot tell capture failed will press again. | HF-04a line 92 |
| FP-09 | On leaving a view, interactive focus restores to a named, visible, non-committing control, and never to a control whose activation commits a gameplay action or an irreversible choice. | FP-14 | Controller support is stated as a requirement and claimed nowhere. Two consequences a reviewer should hold onto. First, the accidental-cast guarantee is structural, not vigilant: it comes from classifying input before routing it (FP-11), from the drain clearing held edges and demanding neutral re-arm (FP-03), and from `submit_action` being reachable only from a `gameplay` step at RL2 (FP-10). An interface that relies on the player not pressing the wrong thing has not met the requirement. Second, aim is part of what the drain releases: free and focused aim are aim states of a ticking encounter (TH-02 MA-06 line 39; TH-02 MA-07 line 40), the input context is set and held input released together (TH-02 MI-02 line 75), and a view that leaves an aim pose live under a menu is showing a lie about what a release would do.
