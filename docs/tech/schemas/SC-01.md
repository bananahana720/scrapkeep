## Contract

### What this contract fixes

Five types, one ID grammar, one placeholder rule for unanswered values, one closed rule vocabulary for admission and load, one save treatment per HF-06a row and the qualification obligations TH-22 executes. Everything a product answer owns stays a placeholder naming its question.

TH-07 owns slot states, milestones, respec and the tree shape as a runtime contract. TH-04 owns what a slot means for an action. TH-08 owns the rebuild these definitions feed. HF-05 owns identity, the gates, the admission states and both diagnostic shapes. HF-07a owns every save field and HF-09 owns migration. This contract cites them and adds definitions only.

| T2 | Class kit | embedded-record | none | T1 at `kit` |
| T3 | Slot definition | schema | `slot` | none |

### Identity, version and placeholder rules

These rules apply to every type below. They are written so SC-02 to SC-08 can adopt them unchanged and TH-20 can reconcile the type tokens into one catalogue grammar.

| ID | Rule | Source |
| --- | --- | --- |
| SI-01 | **Domain ID grammar.** ASCII segments joined by `.`, at least two (SP-13). Each segment starts with a lowercase letter and continues with lowercase letters, digits or `_`. The first segment is the defining type's token from the table above. Resolution never parses the token; an ID is compared exactly and its expected family travels on the referring field (SI-05). | HF-05 lines 18, 22; HF-06a line 24 |
| SI-02 | **Reserved illustrative prefix.** An ID whose first segment is `example` is an illustrative placeholder, and the structural gate rejects it (SA-02). No record in this contract can be admitted as written, so no example becomes canon. | TADR-003 line 35; HF-05 line 50 |
| SI-03 | **Embedded identity.** A class kit and a milestone node have no domain ID. A kit is addressed as its character ID plus the field path `kit`; a node as its tree ID plus `nodes[key=<key>]`. Both forms are HF-05's `referrer` form. | HF-06a line 42; HF-05 line 111; HF-06a row F-03 |
| SI-04 | **Node key grammar.** One segment of the SI-01 form, unique within its tree and compared exactly. A key is a string and never a number. The grammar is fixed here and the vocabulary is Q-P11's (SP-17). | HF-07a line 130; HF-06b line 34; TH-07 PT-13 at line 69 |
| SI-05 | **References.** A reference field holds one domain ID string, or null where its field row says so. Its expected family is fixed by the field definition. A foreign family is named by its HF-06a row until its producing card admits a type token. | HF-05 lines 22, 51; HF-07a line 37 |
| SI-06 | **Layout version.** Every T1, T3 and T4 definition carries `schema_version`, the integer layout of its type, which this revision fixes at SP-12. An embedded record takes its parent's layout. A layout this build does not support fails SA-04. | HF-05 line 50; TADR-003 line 45 |
| SI-07 | **Gameplay content revision.** A change to any field of T1 to T5 is a gameplay change needing a distinct gameplay content revision, unless validation establishes that only presentation references changed. A revision is never reused with a different meaning. An ID is never reassigned to an unrelated definition, and a node key is never reused for a different position in its tree. | HF-05 lines 18, 23, 24 |
| SI-08 | **Placeholder values.** A value this contract leaves to an open question is the string `unset:` followed by one or more registered question IDs joined by `+`, such as `unset:Q-P10+Q-P11`. A placeholder may stand wherever a field's content value column reads `unset:`. The structural gate accepts only that form (SA-07), and the semantic gate refuses any definition still carrying one (SM-01), because unknown required rules block admission and a validator may not invent a value. | HF-05 lines 51, 54 |
