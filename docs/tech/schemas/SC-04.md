## Contract

### What this contract fixes

Seven definition types, their fields, identity and version rules, references, diagnostics and illustrative records; the reference map to three foreign HF-06a rows; the save exclusion for both rows with its paper roundtrip expectations and qualification obligations; and thirty-two tunable parameters. Every value no cited source states is a `SYMBOLIC` token naming its parameter row and question.

It fixes no count, duration, budget, roster, objective type or behaviour. Because every behaviour vocabulary and budget is unset, **no production record of this family can pass admission until the named questions are answered** (HF-05 line 51; TH-06 line 122). That is the intended consequence, not a gap in the schema.

### Rules shared by every type

1. **Identity.** A domain ID is an opaque, nonempty, case-sensitive string compared exactly, issued with its definition and never reassigned (HF-05 line 18), unique across the admitted catalogue (line 22). This family imposes no grammar beyond that, with one exception: the prefix `illustrative.` is reserved for the illustrative records in this document and is rejected at admission, as S0-05 rejects its proof prefix (HF-05 line 188), so no example can become canon by being copied.
2. **Version.** No definition carries its own revision field. Its version is the gameplay content revision of the catalogue that admits it (HF-05 line 23). A gameplay-affecting change keeps the ID and requires a distinct gameplay content revision; reusing a revision with a different gameplay meaning is forbidden. A presentation-only replacement keeps the revision only after validation establishes identical gameplay definitions (line 24). A change to a type's field list is a change to the schema script inside the candidate and follows the same rule.
3. **References.** A reference is a domain ID string resolved as the pair of the run's pinned revision and that ID (HF-05 line 27) with an expected family. It is never an engine path, a UID or an `ext_resource` link. Retrieved engine documentation states that UIDs keep references intact across renames; HF-05 line 18 still excludes the engine UID from durable identity, and resolution by ID is what TH-06 line 201 and TH-14 line 98 require.
4. **Presence.** Every field listed for a type is required as a key. A field typed `or null` accepts an explicit null. An absent key, an unknown key or a wrong type rejects the candidate; nothing is defaulted (HF-05 line 51; TADR-003 line 31).
5. **Symbolic values.** A `SYMBOLIC(ST-nn; Q-xxx)` token is a named unset value. It is never an admissible value, so a record still carrying one is rejected at the structural gate (SD-05).
6. **Behaviour identifiers.** A `behaviour` field holds a reviewed behaviour identifier (TADR-003 line 23) from a vocabulary its parameter row leaves unset. An identifier outside the admitted vocabulary is an unknown required rule and blocks admission (HF-05 line 51).
7. **Immutability.** Admitted definitions are immutable shared values; Encounter builds fresh owned records from them and never writes back (HF-05 lines 35 to 39; TH-06 line 81). No field holds per-run state, a live count, a health value in play, a generator seed or a stream position (HF-03a line 46; TH-14 line 78).
8. **Validation owner.** Every diagnostic below is ContentAdmission's (HF-03a line 34). An editor tool may call the validator and holds no second truth.
9. **Value types.** Every field has a value type SD-03 checks: a primitive (`id-string`, `string`, `int`, `bool`, an array or an enum), a `behaviour` identifier, a type defined in this contract, or one of the named value types below. A named value type's form is fixed by its question's answer; until then SD-03 can check only that the value is of that type, and a `SYMBOLIC` placeholder is rejected by SD-05 first.

| Named value type | Form | Form fixed by | This contract's choice |
| --- | --- | --- | --- |
| `DurabilityValue` | A non-negative number in the unit and precision the answer fixes | Q-P25 | That durability is one number |
| `CommitmentBudget` | A record stating what counts as one commitment and how many may be in flight | Q-E10 | That the budget is one record on the admission record |
| `PressureBudget` | A record of bounds on arrival rate, concurrent arrivals and live population | Q-E10 | That the three bounds travel together |
