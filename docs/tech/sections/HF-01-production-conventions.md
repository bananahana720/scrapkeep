## Contract

### Path ownership

Paths are repository-relative. `*` matches one path component; `**` matches descendants, including a file directly inside the named directory. Semicolon-separated globs are a union. Rows are disjoint. An unlisted path requires an explicit ownership amendment before a future card can claim it. No broad `native/**` lease follows from this table; the coordinator assigns exact files inside a family. Role names describe responsibility, not permanent agents.

The `native/` directory is the Godot root. Existing `native/tests/`, `native/proofs/` and `native/integration/` remain operational proof code and fixtures. The other native implementation families and `source-assets/` below are reserved contracts, not directories created by HF-01. Group each content unit's scenes, definitions and runtime asset inputs under the same `native/content/<unit>/` parent. `<unit>` is a path grouping, never a durable gameplay ID.

### Contribution rules

Use Godot 4.7.2 standard edition and typed GDScript. Type function inputs/returns, mutable domain records and collections; validate loaded values and references at admission. Dynamic engine boundaries must narrow and validate values before owned records consume them. Keep applicable static warnings and justify any scoped suppression. Existing proof preload exceptions and the stricter inferred-declaration setting are recorded in the scaffold; they are not permission to weaken production checks. HF-03/HF-04 own the detailed module and runtime contracts. C#, C++ extensions or another gameplay language require an amended TADR-001 and a measured need.

Use snake_case paths, functions, variables and signals; PascalCase classes and nodes; CONSTANT_CASE constants and enum members. Keep exact path case in references, including after export. Retain established documentary names and existing `tadr-002` proof directories rather than renaming historical files for style. Use tabs, UTF-8, LF, a final newline, double quotes by default and no statement-ending semicolons in GDScript. Follow the linked GDScript guide for declaration order and readable wrapping. Existing JavaScript keeps CONTRIBUTING's ES modules, two spaces, double quotes, semicolons and installed Prettier. Format only changed applicable files.

Scene composition may reference a canonical gameplay `.tres`; it cannot override authoritative damage, milestones or compatibility. Stable domain IDs survive filename/display-name changes. Engine paths and UIDs do not become save IDs. Retain existing sidecars with their owner file, inspect reference changes during moves, and require an appropriate reference/round-trip proof before admitting a move. Shared admitted Resources remain immutable; mutable session records are fresh instances owned by the session. Definitions contain no accumulating run state.

Before admitting an asset, retain its editable original and provenance: source URL or local origin, creator/provider, license evidence, transformations, intended use, units/axes and applicable rig/animation facts. Link its reviewed runtime input back to the master. Keep import settings with that input; generated cache is replaceable and untracked. Source masters outside `native/` are not runtime resources. If a later card uses `.gdignore` inside the Godot root, its contents become unavailable to Resource loading; it is not an export-only filter. Do not hide runtime dependencies that way. No new third-party package, download, LFS migration or paid tool follows from this convention.

Validation follows TADR-003: structural/domain checks, cross-reference/semantic checks, then one versioned catalogue and asset manifest. A missing ID, unsupported version or failed reference rejects admission with a diagnostic. It cannot substitute a default or silently change an existing save. Authoring tools may emit canonical Resources but must not maintain an independently editable copy. Candidate concept art and names remain references until the appropriate product/content card admits them.

The coordinator owns shared navigation, the technical-section index, BACKLOG definitions, TRACKING execution and final TECH_BIBLE assembly. A writer edits its leased section and evidence only, and returns proposed shared changes for serial admission. Durable boundary changes require the owning ADR. This section is one contribution contract; it does not replace any authority document.

For commits and PRs, inspect the actual branch/base and owner changes first. Keep writing agents isolated, stage only assigned files, and commit the review candidate locally. The coordinator admits reviewed changes serially and records candidate, review and integrated identities separately. Use a title naming the concrete change and a body explaining the resulting contract, source decisions, checks and material limits. Include an ADR change when needed. Preserve historical receipts and do not stage generated cache, exports, disposable evidence, secrets or unrelated changes. Existing private-remote authorization remains governed by CONTRIBUTING and TRACKING. A convention edit creates no remote, PR publication, push or release authorization; experimental branches remain local unless separately authorized.

### Reviewer definition of done

1. Confirm the exact approved card, base, lease and required admitted dependencies; no ready card alone authorizes implementation.
2. Classify every changed path once and reject protected-path overlap or an unleased shared-file edit. Include sidecars, fixtures and generated destinations in the review.
3. Check naming/style, typed boundaries and ownership against TADR-001/TADR-003; reject duplicate gameplay truth or mutable admitted definitions.
4. For assets, inspect provenance, editable source, import settings and reference validation. Require the TH-19 repair/proof before production import admission; concept art is not launch content.
5. Update the owning documentation and ADR when applicable through the coordinator. Keep numerical/product unknowns explicit and block implementation that needs their answers.
6. Run `npm run check:scope -- <base> <candidate> --no-build` for a documentation-only candidate, then the named checks. HF-01 requires `npm run check:docs`, `npm run check:project`, five-column/unique-path coverage and contract scenarios. Use `check:docs -- --report artifacts/local/tasks/HF-01/check-docs.json` to keep this task's receipt inside its lease.
7. For later browser changes, run CONTRIBUTING's `npm run verify` and applicable browser checks. Native checks must come from that authorized card and the engineering handoff; browser passes do not qualify the native game. Do not run a build for this documentation card.
8. Supply source identity, commands, outcomes, retained evidence and gaps for fresh independent review. Only the coordinator admits, reruns applicable checks on integration, and records completion. State separately any human, hardware or production qualification still missing.

## Scenarios

- A native attack-definition card selects `native/content/<unit>/definitions/attack.tres`. Content owns that file; its scene can reference it, but a scene damage override fails review. Placeholder paths name no approved attack or roster.
- A material import brings a runtime input and adjacent `.import` settings under one assets row; its editable master belongs in `source-assets/`. The present ignore/harness policy blocks production admission until TH-19's repair and proof exist. A `.godot/imported/` cache file is disposable, never the canonical master.
- A writer proposes moving orchard code into `native/runtime/`. The protected browser boundary rejects the move even if both files would compile. Consolidation needs explicit approval and its own contract.
- A scene rename retains the stable gameplay ID, reviews UID/path references and proves round-trip/export references under an authorized check. It cannot rewrite a save ID to match the new filename.
- A documentation writer changes only this section. The scope check selects docs/project checks and scenario review. No engine, build, export or CI run is justified by that change.
- Re-running a proof writes fresh disposable results. Retaining a new receipt requires source identity and a new durable record; it cannot overwrite an earlier dated result or label synthetic success as human gameplay evidence.
