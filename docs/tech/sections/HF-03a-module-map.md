## Contract

### One session authority

`Session` is the sole application/session authority. It creates and supplies the other modules, holds the live run and permanent profile across replaceable encounters, and authorizes lifecycle transitions. It does not acquire permission to mutate another module's records by constructing that module. The production composition has one live Session and one active Encounter coordinator. Replacement detaches the outgoing encounter's command routes and scoped result connections before the replacement may advance; stale results cannot change the continuing run.

The table is the complete module allocation for this foundation contract. Record names are conceptual typed record identities, not claims that classes or files already exist. Each record includes its nested mutable fields and owned collections. Subsystems such as attacks, enemies, equipment rules, progression, routes, devices and companion behavior are composed controllers operating within the listed owner's boundary. They are not additional autonomous mutation owners. A future field must enter a named record; splitting authority or adding a module requires an explicit contract revision before implementation.

HF-01 reserves `native/runtime/` for Session, Encounter, CollisionQueries, ContentAdmission and Persistence implementation, and `native/presentation/` for InputAdapter and Presentation. Authored schema scripts and canonical `.tres` definitions remain under `native/content/<unit>/definitions/`; content-admission service code does not become a second authored catalogue. HF-01's file roles govern leases; this table governs runtime records.

Beyond those common allowances, imports are limited to the table. An injected service reference is allowed only for the listed commands or readers, never foreign writable fields.

Dependency direction follows the importing consumer or composition owner toward the supplied module. Session composes all six services, Encounter depends on CollisionQueries and InputAdapter, and Persistence depends on ContentAdmission's resolver contract. The other modules have no module-to-module import. Returned values and reading a producer's published result use that existing edge; they do not create a reverse dependency. For example, Session calls Encounter's `read_committed_results` and Presentation's `read_ui_requests`, then explicitly routes the returned values. Presentation holds no callback that mutates Session. A scoped notification may announce available results, but must not perform a gameplay transition on delivery. HF-03b must enumerate these distinctions in its reproducible graph and walkthroughs.

### Record meanings and lifetime

These definitions partition mutable state. They do not prescribe serialization field types, numerical tuning or full command payloads. HF-03b owns dependency edges and attack/equipment/encounter interface walkthroughs; HF-05 owns definition identities; HF-07a owns save fields. Concrete payload schemas remain with their named producer cards.

- Session's `SessionControl` holds active encounter identity, service references, input/modal/pause coordination and transition admission status. `RunState` holds run identity, selections, inventory/equipment, accepted routes and generation decisions, resolved rewards/offers, run-level random state, companion assembly, revival/terminal facts and the latest completed-level checkpoint in live memory. `ProfileState` holds discovery knowledge and permanent option unlocks. `EffectiveBuild` is the rebuilt derived effect/stat set from current selections and admitted definitions. `PendingTransition` holds the proposed run/profile change, transaction identity and waiting/error status until the durable result permits completion. These records survive encounter unload; they are disposed or replaced only through Session lifecycle commands.
- Encounter's `EncounterState` holds actors' immediate health, authoritative poses, movement intent, resources/cooldowns, wave/objective state, active devices/companion action state and prepared actions. `TickState` holds the encounter's invocation/tick position, pause eligibility and update phase. `AttackLedger` holds attack commitments, declared windups, resolved geometry, targets, random outcomes and applied-result identities. `EncounterRandomState` holds the encounter's mutable generator position. `EncounterInbox` holds submitted commands pending the owned advance. These records belong to one encounter identity and end on retirement. The Session supplies initial build and run data as values; Encounter cannot keep a writable RunState alias.
- CollisionQueries' `CollisionWorldState` holds the attached physical-world/body bindings and synchronized query-world state. Engine integration may update physical bodies; CollisionQueries is the sole application module that drives or interprets those updates. `QueryBatchState` holds request ordering, query scratch data and the current movement/contact results. These are encounter-bound, discarded with the world. A body transform used for a query is a physical-world projection; Encounter alone commits the returned authoritative gameplay pose. Presentation's interpolated transform never feeds this world.
- ContentAdmission's `CatalogueAdmissionState` holds the staged candidate, validation findings and admission status. `CatalogueRegistry` holds revision-to-handle mappings, current eligible revision and retained revision references. Session's run pin selects a revision without modifying that catalogue. Admitted Resources and their published manifest are immutable shared definitions, not mutable records in this table. A replacement candidate has a fresh identity and must not edit cached Resources still referenced by a run.
- Persistence's `SaveTransactionState` holds the candidate aggregate, transaction/generation identity and commit status. `DurableAggregate` is the validated last committed JSON projection of profile, checkpoint and lifecycle facts; it is separate storage from Session's live records. `PreferencesRecord` is the separately versioned preferences data. `RecoveryState` holds inspected generations, migration candidates, preserved-source references and recovery diagnostics. Persistence alone stages or replaces these records and writes their files. It never awards a reward or edits Session memory. Load returns a validated value; Session alone installs it into fresh live records.
- InputAdapter's `PhysicalInputState` holds held controls, prior samples and edge detection. `InputContextState` holds the current routing context and unpublished input frame/request buffers. Clearing physical input cannot mutate a prepared action, pause state, save or run. Input frames are transient and are never restored from a save.
- Presentation's `PresentationState` holds view bindings, previous/current result copies, interpolation, camera, UI display state and pending UI request values. `FeedbackState` holds cosmetic effects, animations, audio voices and presentation-only cue consumption state. They are replaceable from published results. View bindings are not actor ownership; cue consumption does not settle rewards or mark an attack applied. Preferences are consumed as a snapshot, not mutated through the UI's display copy.

### Mutation and import rules

1. Commands request a mutation from its owner. Submission may append to an owner's inbox; only that owner changes its record. The Encounter's command submission cannot advance combat. Actor, animation, UI and signal callbacks must not run a second gameplay step.
2. Cross-module results are detached value snapshots or immutable admitted definition handles. Nested arrays/dictionaries and referenced objects must not retain a writable alias into an owner's record. A `RefCounted`, underscore prefix, typed property, `class_name` or preload constant does not establish read-only access. The implementation must enforce the boundary through API design, copy/immutability policy and focused verification.
3. Session routes committed Encounter results into run/profile transitions. Encounter commits immediate combat and attack randomness once. Session settles each accepted reward/offer/route result once in RunState and rebuilds EffectiveBuild from selections, including removal of old effects. Persistence receives the complete candidate projection. It returns durable success only after a qualified commit; Session holds a critical transition on error and does not resume a spent-revival or terminal transition with unknown durability. HF-07 specifies the protocol and payloads.
4. Copies carrying the same domain facts are distinct records with distinct roles. DurableAggregate is the persisted projection, RunState is live continuity, EncounterState is immediate combat, and PresentationState is display. Reconciliation occurs through explicit results and commands; neither copy grants a second writer of the source. A durable spent-revival or terminal fact takes precedence over an older checkpoint during restore.
5. `class_name` makes a type globally discoverable and usable without a loading expression. `preload` resolves a script/resource at compile time; instantiation remains a separate operation. Both count as dependency edges under the table, including script inheritance, typed fields and scene references. Static access must not hide mutable gameplay state or bypass service injection. See the [GDScript reference](https://docs.godotengine.org/en/4.7/tutorials/scripting/gdscript/gdscript_basics.html).
6. Autoload can keep a Node alive across scene changes, but Godot permits additional instances. A Session autoload is an implementation option, not a selected or tested bootstrap mechanism. If a later card chooses it, only the composition root binds it and supplies explicit service references; gameplay callers cannot use a global name to reach foreign records. Multiple autoloads cannot become independent run/tick authorities. See [autoload](https://docs.godotengine.org/en/4.7/tutorials/scripting/singletons_autoload.html).
7. Scoped signals publish committed results or user requests. A listener cannot turn a result notification into a hidden mutation chain. Session retains explicit transition routing; collision contact signals are interpreted by CollisionQueries and returned for Encounter commitment. Detailed ordering, cancellation timing and overload handling remain HF-04a/HF-04b work.
