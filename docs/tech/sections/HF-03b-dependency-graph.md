### Properties the check reproduces

1. The graph is acyclic. One valid topological order is Session, Encounter, Persistence, Presentation, CollisionQueries, InputAdapter, ContentAdmission, Values. The checker recomputes this with Kahn's algorithm and records the order it found.
2. Session is the only node with no incoming edge among the modules, and every other node is reachable from it. Composition therefore has one root (HF-03a line 19).
3. Presentation, CollisionQueries, ContentAdmission and InputAdapter reach only Values. They are leaves of the module graph.
4. Injection does not add edges. Session injects the frame reader into Encounter on D01 and the resolver into Persistence on D04; the injected reference exposes only D08's and D09's permitted use (HF-03a line 27, last sentence).
5. Return values, published results and notifications travel on the importing side's edge and add no reverse edge (HF-03a line 39). Reading `read_committed_results` on D01 or `read_ui_requests` on D06 is the whole delivery route for gameplay results and UI requests.
6. Definition data supplied to Encounter, CollisionQueries and Presentation must be self-contained immutable values or handles whose reads do not call ContentAdmission. A handle that resolves through ContentAdmission on access is a hidden Encounter-to-ContentAdmission or Presentation-to-ContentAdmission edge and a defect.

### Signals and rendering cannot mutate gameplay

These rules make DoD item 1's prohibition checkable against the list above. They restate TADR-002 lines 24, 26, 30 and 32, HF-03a lines 39, 55 and 61, and HF-04a lines 44, 49 and 53; they add no new authority.

1. A signal connection is a use of an existing edge. Only the module that holds the edge to the emitter may connect to the emitter's signal. Session may subscribe to Encounter, ContentAdmission, Persistence, InputAdapter and Presentation notifications on D01 to D06; Encounter may subscribe to CollisionQueries contact observations on D07; Persistence may subscribe to a resolver diagnostic on D09. No other subscription exists. Presentation may not subscribe to Encounter, because no Presentation-to-Encounter edge exists; it receives snapshots when Session calls `present_snapshot`.
2. The emitter never references the subscriber's type, record or command. Its payload is an identity or a detached value snapshot (HF-03a line 56).
3. A handler may only record that a result is available or enqueue a request for its own owner. The read and the routing happen at that owner's explicit control boundary (HF-04a line 26). A handler performs no tick, no `submit_action`, no run or profile transition, no damage, no target choice, no random draw and no call on a second edge (HF-04a line 49). A pause does not make a handler safe (HF-04a line 53).
4. Engine signals such as timer timeouts, body or area contacts, animation tracks and audio completion terminate in the owner of the receiving record and never cross a module edge. Collision contact signals are interpreted by CollisionQueries and returned on D07 for Encounter to commit (HF-03a line 61).
5. No global bus, autoload reach or globally named type may carry gameplay data between modules that have no listed edge (TADR-002 line 24; HF-03a lines 59–60). A signal whose subscriber and emitter have no listed edge is a hidden edge. Report it as a defect against this list; do not add the edge.
6. Presentation holds detached copies only. It reads no owner record, performs no physics query, chooses no target, marks no attack applied and rerolls no loot, miscast or route offer (TADR-002 line 30; BIBLE line 608; HF-03a line 51). A UI control records a `UiRequest` value; it calls nothing. An art change to a tool's reach changes combat only through the definition and Encounter's resolution on D07, never through a view (ADR 0003 line 13).

### Walkthrough conventions

Each walkthrough under Scenarios is a step table with these columns. `Caller → target` names the two modules of the edge used. `Edge` is a D identifier from the adjacency list or the word `local`. A `local` step changes only the caller's own records inside its own callback and makes no cross-module call, so it can use no edge at all, listed or unlisted. `Interface` names the command invoked or the published result read; for a `local` step it names the owned record or the caller's own command. `Callback` names the HF-04a callback class and, for C-TICK, the phase. A step that could only be completed by an unlisted edge is written with `DEFECT` in the Edge column and entered in the unlisted-edge register; no such step was needed, and the register records the routes rejected to keep it that way.

The checker verifies, for every non-local step, that the edge exists, that From and To equal the caller and target, and that each backticked interface belongs to the target module's exposed commands or published results in the HF-03a table. It verifies that no `DEFECT` row exists and that HF-04a's own scenario arrows use only listed edges.
