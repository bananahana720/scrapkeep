## Contract

### The save column

Every HF-06a row receives exactly one of three values. The values are the three cases of TADR-003 line 45.

| Value | Meaning | Required companion cells |
| --- | --- | --- |
| `json-projection` | The aggregate holds a mutable record whose values are instances, selections, assemblies, knowledge or facts of this row's subject. The record is produced from live RunState, ProfileState or PreferencesRecord (HF-03a lines 45 and 49) and round-trips through the JSON persistence codec. | Authoring codec, save projection and proof owner, all nonempty; the proof owner is TH-22. |
| `transient-reconstructed` | The row's subject exists at runtime as a mutable record or presentation state that is rebuilt on load from the aggregate and the admitted definitions. It never enters the aggregate. | A rationale naming the HF-03a record that holds the state and what it is rebuilt from. |
| `immutable-by-id` | The aggregate holds no mutable record for the subject. Either the subject is an authored definition resolved by gameplay content revision and domain ID and appears at most as an ID reference inside another row's projection, or the subject has no definition and no runtime state and its only durable trace is the admitted catalogue the envelope pins by content revision. | A rationale naming which of the two cases applies and, for a definition, which projection references it. |

Rules that apply to every row:

1. No Resource is serialized as a live engine object. A projection carries domain IDs (HF-05 line 18) and the envelope carries one gameplay content revision (TADR-004 line 28; HF-05 line 23); load resolves each `(revision, ID)` pair through the pinned catalogue (HF-05 line 27). Engine nodes, live pointers, render transforms, particles, audio voices and input-held state are never save identities (TADR-004 line 34). Whole-scene serialization is the rejected option at TADR-004 line 20.
2. The value follows the row's subject as HF-06a treated it. A `schema` or `embedded-record` row is a definition, so it is `immutable-by-id` unless the run or profile holds a mutable projection of its instances, in which case it is `json-projection`. An `excluded` row is either runtime state (`transient-reconstructed`) or guidance with no state (`immutable-by-id`, second case). The `Case` column records which reading applies, and the paper check enforces the pairing.
3. A candidate instance row (a region N-002 to N-006, a pilot N-007 to N-011) is `immutable-by-id`. The projection that references one of them belongs to its family row (F-05, F-01).
4. Every projected ID is a JSON string. S0-08 observed that the engine parses every JSON number as a float and restores ints only through a boundary cast (S0-07 line 45; S0-08 line 47). A domain ID is an opaque token (HF-05 line 18), so it is encoded as a string and never as a number; node keys inside a tree selection follow the same rule. Numeric fields such as counters and generations are declared int or float by HF-07a and cast at the boundary as S0-07 does.
5. An ID that the pinned revision cannot resolve fails visibly and holds the affected restore or transition (TADR-004 line 34; HF-05 line 27). It is never remapped, rerolled or dropped (TADR-003 line 41).
6. Derived state is never projected. `EffectiveBuild` (HF-03a line 45), including active recipe bonuses, derived stats and compatibility outcomes, is rebuilt from restored selections and compatible content (TADR-004 line 26; HF-05 line 56), so reload cannot stack a bonus or duplicate a reward (Bible line 465).

### Question-shaped rows

Each question-tagged row carries a treatment that holds under every candidate answer. The questions are in `proposed` state at TRACKING EV-0144; the proposals recorded there are not assumed anywhere in this section.

- [Q-P15](../../../BACKLOG.md#q-p15) leaves open companion chassis, components, commands and device capacity, lifetime, recall, resource and cross-level persistence rules. Rows F-06, F-07, N-016 and N-027 carry it. Under every answer the companion assembly is checkpoint content by TADR-004 line 26 and projects as chassis, component and command-capability IDs, so F-07 is `json-projection`. Under every answer a device definition is immutable and a deployed device's in-level state is EncounterState (HF-03a line 46), so nothing but IDs and typed counters can ever be projected. What the answer decides is whether any device fact crosses a level boundary. TADR-004 line 26 reserves the carry-over fields for exactly that decision, so F-06 and N-027 name `checkpoint.device-carry-over` as a projection whose field set may be empty. `json-projection` holds under both the no-persistence answer (empty set) and the persistence answer (populated set); `immutable-by-id` would hold only under the first. N-016's compatibility declarations stay definitions and their outcome stays derived under every answer.
- [Q-E09](../../../BACKLOG.md#q-e09) leaves open which discovery facts become durable immediately and which wait for a completed-level or terminal commit. Rows F-08, N-017, N-026 and N-028 carry it. Under every answer the profile projection is the same set of discovery, recipe and unlock IDs persisted once (TADR-004 line 26; Bible lines 462, 463 and 586). The answer decides when an entry commits, and every commit uses the transaction protocol at TADR-004 line 28 so a duplicate converges and no award is duplicated (Bible line 465). An immediate answer commits the profile entry in its own generation; a deferred answer commits it with the next checkpoint or terminal aggregate. Neither adds a save field this section assumes; whether a durability class exists as a definition field is SC-08's, and no save-side class field is required. N-028's run identity, checkpoint and lifecycle facts have the same shape under every answer; Q-E09 only orders the profile commit relative to the terminal fact, which is HF-07b's protocol.
- [Q-P14](../../../BACKLOG.md#q-p14) leaves open recipe eligibility, bonuses, tradeoffs and disclosure. Rows F-08, N-015, N-016, N-017, N-025 and N-026 carry it. Under every answer eligibility, bonuses and tradeoffs live in immutable definitions, knowledge is a set of recipe or discovery IDs, and any pre-discovery disclosure state is knowledge keyed by the same IDs. Owned equipment and equipped selections are sets of item IDs whatever the compatibility rules are. No projection shape changes with the answer.

Q-P16 is not registered on this card. F-04 and N-028 are the only matrix rows whose rationale names it, because the unfinished-level interruption rule at TADR-004 line 32 could add a location or health field to the checkpoint. That field would be HF-07a's and HF-07b's; it would not serialize EncounterState, so both rows' values hold under every Q-P16 candidate. Scenario C12 walks that answer across N-019 and N-023 as well; those two rows hold for the reason their own rationales already give, and neither names the question.
