## Contract

### Two documents and one naming rule

The aggregate is one JSON document. The preferences record is a second JSON document with its own root, because changing sound or UI scale must not rewrite gameplay progress (TADR-004 line 24). Neither document is an engine scene, a Resource or an object graph; whole-scene and engine-object serialization is the rejected option at TADR-004 line 20.

A field's name in this contract is its path from its document's root, with `[]` marking a member of an array element. Preferences names carry a `preferences.` prefix because both documents define `schema_version` at their own root and downstream cards must be able to cite one without ambiguity. `preferences.ui_scale` is therefore the key `ui_scale` at the root of the preferences document, while `run.checkpoint.next_entrance` is the key `next_entrance` inside `checkpoint` inside `run` in the aggregate.

One rule splits the run's own facts between two containers and is stated only here. A fact that exists at the run-start transition, before any level has completed, lives under `run.start.*`. A fact produced by completing a level lives under `run.checkpoint.*`. That is why `run.checkpoint` is null while a started run is already playable, why the character, the first entrance and the generator streams a run begins with are `run.start` fields, and why nothing under `run.start` is rewritten by a later commit. The Q-P16 reservation sits beside both as `run.interruption`, because an unfinished level can be interrupted inside the run's first level, when `run.checkpoint` does not yet exist.

Downstream cards cite a field by this name and a group by its anchor: [`#envelope-fields`](#envelope-fields), [`#profile-fields`](#profile-fields), [`#run-identity-fields`](#run-identity-fields), [`#run-start-fields`](#run-start-fields), [`#checkpoint-fields`](#checkpoint-fields), [`#lifecycle-fields`](#lifecycle-fields) and [`#preferences-fields`](#preferences-fields). The anchors are stable and do not change when a heading is reworded. HF-07b, HF-08, HF-09, TH-11 and TH-21 reference fields by these names.

### Types

The type column uses this closed vocabulary. Every type is a JSON type plus the restriction this contract places on it.

| Type | Meaning |
| --- | --- |
| `string` | A JSON string. Nonempty unless the field's rule says otherwise. |
| `id-string` | A JSON string carrying a domain ID: opaque, nonempty, case-sensitive and compared exactly (HF-05 line 18). It is resolved as the pair of `content_revision` and this value (HF-05 line 27). Never a number, because rule 4 of HF-06b line 34 makes every projected ID a string. |
| `int` | A JSON number written from an integer and restored through a boundary cast to int. It is never fractional and never relied on as a float. The cast exists because the engine parses every JSON number as a float and stringifies every number as a float (S0-07 line 45), so an integer that is not cast back would leak a float into the contract. |
| `float` | A JSON number that is genuinely continuous and needs no int cast. Only the preferences record uses it. |
| `bool` | A JSON boolean. |
| `object` | A JSON object whose keys this section names, or, where stated, whose keys another card names. |
| `array of T` | A JSON array whose members are all of type T, in the order the field's rule fixes. |
| `map of string to int` and `map of string to float` | A JSON object used as a keyed set of values of that one type, whose key set the field's rule assigns to another decision rather than fixing here. |
| `X or null` | Either X or JSON null, with the rule stating exactly when null applies. A null is a stated state, never a missing key. |

No numeric field in the aggregate is a float. The only numbers in the aggregate are `schema_version`, `generation`, `run.checkpoint.route[].sequence` and the values of `run.checkpoint.device_carry_over[].counters`, and all four are `int` cast at the boundary. A 64-bit generator state is a `string` and not a number, because a JSON number parsed as a float cannot carry a 64-bit state word exactly and a silently rounded state would restore a different stream.

### Presence

| Presence | Meaning |
| --- | --- |
| `always` | The key is present in every committed document of its record. |
| `when-present` | The key is present exactly when its containing object is an object rather than null. `run.*` fields are present when `run` is an object; `run.start.*` fields are present when `run.start` is an object, which is whenever `run` is; `run.checkpoint.*` fields are present when `run.checkpoint` is an object. |
| `element` | The key is present in every element of its array. An empty array has no elements and therefore no missing key. |

A key that is required is written even when its value is an empty array, an empty object or null. An absent required key is invalid data and fails validation; it is never treated as a default.

### Rules that apply to every field

1. No engine identity is ever a field value. Engine nodes, live pointers, render transforms, particles, audio voices and input-held state are not durable save identities (TADR-004 line 34), and no field here holds a node path, a scene path, a resource path or an object reference.
2. Derived state is never stored. `EffectiveBuild`, active recipe bonuses, derived stats, compatibility outcomes, current health, dashboard availability states and run playability are rebuilt from the restored selections and compatible content (TADR-004 line 26; HF-05 line 56). Playability in particular is derived from `run.lifecycle.terminal`, not stored beside it.
3. Every reference to authored content is a domain ID resolved as the pair of `content_revision` and that ID (HF-05 line 27). An ID the pinned revision cannot resolve fails visibly and holds the affected restore. It is never remapped, rerolled or dropped (TADR-004 line 34; TADR-003 line 41).
4. A generator seed never replaces a stored outcome. Offered options, accepted route steps, accepted generation decisions and resolved rewards are stored as what actually happened, and `run.checkpoint.rng_state` exists to continue generation, not to recompute any of them (TADR-004 line 26; HF-05 line 58).
5. Array order is fixed by the field's rule so that two serializations of the same state are identical, which is what lets a duplicate transaction be recognised as unchanged rather than rewritten (TADR-004 line 28; S0-07 line 45 on byte-for-byte re-serialization).
6. The preferences record holds no gameplay progress and no domain ID. No field in it names a character, item, tree, recipe, unlock, region or device.
7. A field whose value set depends on an unanswered question is named here as a container with a stated type, and the values or keys inside it are left to the answer. Naming the container is not answering the question.

### Field tables

Sixty-nine fields in seven groups. Every row carries a type, an owning module and record from HF-03a, and a source or question ID. The `HF-06b group` column gives the projection group from HF-06b lines 55 to 71 that the field satisfies, or `envelope` for an envelope identity key, `container` for a structural container HF-06b does not name, or `reserved` for the Q-P16 reservation. HF-06b groups facts, not aggregate paths, so a `run.start.*` row carries the group of the fact it projects: moving the character selection out of the checkpoint changes where the fact is written, not which HF-06b row it satisfies.

### What the envelope deliberately does not carry

The envelope has exactly six keys: `schema_version`, `content_revision`, `generation`, `transaction_id`, `profile` and `run`. Four identify the format, the content, the ordering and the transaction, as TADR-004 line 28 requires. Two are containers. No seventh key exists, and in particular the envelope carries no field that only one candidate policy would need.

| Rejected envelope field | Why it is not there |
| --- | --- |
| A durability class, commit class or write-reason key | Only the immediate half of Q-E09 would need it, and the deferred half would carry a dead key. A durability class, if one exists at all, is a definition field on the content side, and the save shape is identical under both answers: the same set of IDs, committed once per transaction. |
| An interruption kind, a resume mode or a mid-level flag at envelope level | Only one Q-P16 candidate would need it. The single reservation this contract makes for Q-P16 is `run.interruption`, which is inside `run` beside the checkpoint, is null under the candidate that stores nothing, and names no key of its own. |
| A generator seed | TADR-004 line 26 says a seed alone cannot justify rerolling stored options. A seed at envelope level would invite exactly that. `run.checkpoint.rng_state` carries generator state per stream and never substitutes for a stored outcome. |
| A `playable` flag | It is derived from `run.lifecycle.terminal` (rule 2). Storing it would create a second, conflicting authority over the fact TADR-004 line 30 makes decisive. |
| A checkpoint generation or a checkpoint timestamp | The aggregate's `generation` already orders whole documents, and a checkpoint and the lifecycle facts committed with it are consistent by construction. TADR-004 line 30 is satisfied by committing a new aggregate when the spent flag changes, even when the checkpoint is unchanged, not by a second ordering value. |
| A schema or content revision inside `run` or `profile` | One document has one `content_revision` (TADR-004 line 28). A second copy could disagree with the first and would create a resolution rule that no source states. |
| A migration marker, backup pointer or recovery status | Recovery, preserved sources and diagnostics are `RecoveryState` (HF-03a line 49) and belong to HF-08 and HF-09, not to a committed aggregate's shape. |
| A results-screen, reward or presentation key for a won run | `run.lifecycle.outcome` is the whole durable consequence of winning. What a won run shows, grants or unlocks afterwards is a product decision no source has made, and a key for it here would presume one. |

The preferences record carries `schema_version` and the four settings. It carries no `content_revision`, because it references no authored content, and no `generation` or `transaction_id`, because TADR-004 line 28 gives those to the aggregate's transaction and line 24 separates the two records precisely so a preference change is not a gameplay commit. Whether a preferences write uses a transaction protocol of its own is HF-07b's and HF-08's; adding a field for it here would presume their answer.

## Scenarios

Eleven worked scenarios. Each one names what changes and, more importantly, what must not. None of them was executed; they are the contract read against its sources.

**S1. First launch, no run.** The aggregate is `schema_version`, `content_revision`, `generation`, `transaction_id`, `profile` with three empty arrays, and `run` null. No `run.start` exists, because there is no run to have started. `run` is the only null container at this point, and it is the only moment at which it is null. The preferences record exists independently with its own `schema_version`.

**S2. First level completed.** `run` is already an object from S9 with `run.run_id`, `run.start` and `run.lifecycle`, and `run.checkpoint` becomes an object: the slots reached with their unlocked flags and node key prefixes, the owned instances and the equipped selection, the settlements already resolved, the offers already made with the options actually presented, the accepted route step, the accepted generation decisions, the generator streams that must continue, the companion assembly, the device carry-over list and `next_entrance`. `generation` increases and `transaction_id` is new.

**S3. Reload after S2.** Every field restores by value. `EffectiveBuild`, derived stats, active recipe bonuses and dashboard availability are rebuilt and appear in no field. `run.checkpoint.offered_choices` is restored rather than regenerated, so the same two destinations are still on offer, and `run.checkpoint.resolved_rewards` prevents a completed settlement from granting a second instance.

**S4. Duplicate delivery of the same transaction.** The same `transaction_id` arrives twice. The second delivery converges on the existing result: `generation` does not advance, no array gains a member, and no settlement in `run.checkpoint.resolved_rewards` is applied a second time. Rule 5's fixed array order is what makes the re-serialized candidate identical to the committed document.

**S5. The standard revival is spent mid-level.** A new aggregate commits with `run.lifecycle.revival_spent` true and a higher `generation`, while `run.checkpoint` is byte-identical to the one before. No checkpoint field records the revival, and no field records the health or placement the player resumes with: under every Q-P16 candidate answer those are encounter values, and the durable fact is the flag alone. A later restore that compares this aggregate with an older one keeps the flag true.

**S6. Terminal defeat.** `run.lifecycle.terminal` commits true with `run.lifecycle.outcome` `lost`, in one generation, before any other playable state resumes. `run` is not set to null and `run.run_id` does not change, so the closed run cannot be reopened by dropping a key. A checkpoint predating the fact cannot override it. Playability is derived from the flag, not from the outcome.

**S7. A preference changes during a run.** Only the preferences document is rewritten. The aggregate's `generation` and `transaction_id` are untouched, no gameplay field moves, and no domain ID appears in the preferences document. This is the separation TADR-004 line 24 requires.

**S8. Both candidate answers to each open question.**

**S9. New run after a terminal run.** The committed `run` is an object with `run.lifecycle.terminal` true. One transaction replaces it: a new `run.run_id`, a fresh `run.start` carrying the chosen `run.start.character_id`, the `run.start.entrance_id` the run begins at and the `run.start.rng_state[]` streams it begins from, `run.checkpoint` null because no level has completed, `run.interruption` null, and `run.lifecycle` with `revival_spent` and `terminal` false and `outcome` null. `profile.discoveries`, `profile.recipes` and `profile.unlocks` carry forward unchanged, because permanent knowledge survives a closed run (BIBLE line 586), and `generation` advances by one like any other commit: it orders the save, not the run. The closed run's own facts are not kept beside the new ones; the aggregate holds one run, and the new `run.run_id` is what says this is a different one. Whether the player may do this while the committed run is *not* terminal is [Q-P39](../../../BACKLOG.md#q-p39) and is not decided here or anywhere in this contract. Under P1 the new run resumes at `run.start.entrance_id`; under P2 or P3 a `run.interruption` object belonging to the closed run is replaced with the new run's null along with every other run field, and it cannot survive into the new run because it is inside `run`.

**S10. First-level revival, then an interruption, with the checkpoint still null.** The run of S9 has completed no level, so `run.checkpoint` is null. The first lethal defeat commits `run.lifecycle.revival_spent` true; no checkpoint is created by it, because a revival is not a completed level. The player then quits inside the same unfinished level. Under P1 nothing further is written: `run.interruption` stays null and the run resumes at `run.start.entrance_id`, which is the resume position precisely because `run.checkpoint` is null. Under P2 a non-null `run.interruption` commits with the keys that answer supplies; it cannot clear `revival_spent`, and it is readable without a checkpoint because it is not inside one. Under P3 either shape holds, and the run still resumes at `run.start.entrance_id`. No answer needs a field that does not exist here, and none of them can reach `run.lifecycle`.

**S11. Final encounter won, then a new run.** The final encounter completes the run. One transaction commits `run.lifecycle.terminal` true and `run.lifecycle.outcome` `won` together; `run` stays present with the same `run.run_id` and the checkpoint it had, so a reload reads a closed, won run rather than a live one, and playability is derived false from `terminal` exactly as it is after a defeat. No reward, no results screen and no unlock is implied by `outcome`: what a won run grants is a product decision, and `profile.unlocks` already holds whatever a settlement actually resolved. The player then starts another run, which is S9 unchanged — the admission fact is `terminal`, and it is true here — and the new aggregate carries `outcome` null again because its `terminal` is false. The one thing this pair is not allowed to do is rewrite the won run's `outcome`, which is written once with `terminal` and never again.
