## Contract

### The four observables

Every stage below names its effect on exactly these four observables. Nothing else is observable at a commit boundary.

| Observable | Definition | Owner |
| --- | --- | --- |
| `C` | The committed aggregate: the one document a restore performed at this instant would read, identified by its `generation` and `transaction_id`. `C` is the whole durable truth of the save. | Persistence / `DurableAggregate` (HF-03a line 49) |
| `S` | The staged candidate set: complete candidate byte images written to storage but not committed. A member of `S` is not durable and is never read as gameplay state. | Persistence / `SaveTransactionState` (HF-03a line 49) |
| `A` | The acknowledgement set: the transaction identities the owner has recorded as durable. It is the gate Session waits on, and it leaves no durable trace; see "Acknowledgement leaves no durable trace" below. | Persistence / `SaveTransactionState` (HF-03a line 49) |
| `L` | Session's live state: `RunState`, `ProfileState` and `PendingTransition` (HF-03a line 45; HF-04a lines 81 and 106), with playability derived from `run.lifecycle.terminal` and never stored (HF-07a rule 2, line 58). | Session |

`C` is written only by a commit. `A` is written only by an acknowledge. `L` may not present a transition as done, release its `PendingTransition` entry or resume playable state until that transition's identity is in `A`.

### The four stages

Every durable transition uses the same four stages in this order, without exception (TADR-004 line 28). The transitions below differ only in what the candidate contains and what the domain-level before and after are.

1. **Stage.** Persistence builds one complete candidate aggregate from the transition's accepted inputs, sets `generation` to the committed generation plus one, sets a fresh `transaction_id`, and serialises it with the array order HF-07a rule 5 (line 61) fixes so that two serialisations of the same state are identical. The candidate is written to storage separately from the committed record. *Before:* `C` is generation `G` with transaction `T`; `S` holds no image for the new transaction; `A` contains `T`. *After:* `C` is unchanged at `G`/`T`; `S` gains the candidate image for `T'`; `A` is unchanged. Nothing about the transition is durable, and `L` still holds the transition pending.
2. **Validate.** Persistence re-reads the candidate bytes from storage, never the in-memory object, and checks them. The checks are: every required key present and correctly typed, with an absent required key treated as invalid data and never as a default (HF-07a line 53); `schema_version` supported by this build; every domain ID resolvable as the pair of `content_revision` and that ID (HF-05 line 27); `generation` strictly greater than the committed generation; `run.lifecycle.revival_spent` and `run.lifecycle.terminal` not weaker than the committed values; and the per-transition checks listed with each transition. A candidate carrying the committed `transaction_id` converges instead of competing (TADR-004 line 28). *Before:* `C` at `G`/`T`; the candidate is untested. *After:* `C` is still `G`/`T`; the candidate is either eligible or rejected; `A` and `L` are unchanged. Validation changes nothing durable in either outcome. A rejected candidate is preserved, not deleted, and never overwrites the source (TADR-004 line 34).
3. **Commit.** Only the candidate that returned eligible from validate, for this exact `transaction_id`, may commit. Commit replaces the committed record through the qualified filesystem protocol TADR-004 line 28 requires and line 38 refuses to accept as proven by a temporary file, a rename, a checksum or a backup alone. A converged duplicate commits nothing and leaves `C` untouched. *Before:* `C` at `G`/`T`. *After:* `C` is generation `G+1` with transaction `T'` and carries the transition; `S` no longer holds `T'` as a candidate; `A` does **not** yet contain `T'`; `L` still holds the transition pending and has not resumed playable state.
4. **Acknowledge.** Only after commit has returned success for `T'` does the owner record `T'` as durable. *Before:* `C` at `G+1`/`T'`, `T'` not in `A`, `L` holding the transition pending. *After:* `A` contains `T'`; Session may release the `PendingTransition` entry, present the transition as done and restore playable state through O4 (HF-04a lines 90 and 113). `C` does not change at this stage.

**The hold rule.** A failure at any stage holds the transition and shows a recoverable save error (TADR-004 line 32). The transition is not reported as saved, `L` does not release it, and a completed revival or terminal transition whose durability is unknown is never continued through. A failure at stage 1 or 2 leaves `C` at `G`/`T` and the transition unperformed. A failure at stage 3 leaves `C` at `G`/`T` with a preserved candidate; whether that candidate is later resolved, discarded or treated as ambiguous is [HF-08](../../../BACKLOG.md#hf-08)'s recovery rule, not this contract's. A failure to acknowledge after a successful commit leaves `C` at `G+1`/`T'` and holds `L`; the transition is durable but not yet released, which is safe in one direction only and is the reason acknowledgement is not the durability record.

### D1: only a validated committed generation can be acknowledged as durable

This is the card's first verification requirement, and it follows from the stage gates rather than from a convention.

| Gate | Statement | Source |
| --- | --- | --- |
| D1.1 | Acknowledge accepts a transaction identity only when commit has returned success for that same identity. An acknowledge attempted earlier records nothing and raises the recoverable error. | TADR-004 line 28 ("only then acknowledges"); S0-07 line 41; S0-08 line 46 |
| D1.2 | Commit accepts only the candidate that last returned eligible from validate, matched by `transaction_id`. A candidate that was never validated, or was validated and then re-staged, is not eligible. | TADR-004 line 28; S0-07 lines 39 and 40 |
| D1.3 | Validate reads the candidate bytes back from storage, so eligibility is a property of what is actually stored, not of the in-memory object that produced it. | S0-07 line 39; S0-08 line 47 |
| D1.4 | A candidate whose `generation` is not strictly greater than the committed generation is rejected, so an acknowledged generation is always the highest committed generation of that save. | TADR-004 line 30; HF-07a line 77; S0-08 line 52 |
| D1.5 | Therefore `A` only ever contains identities of documents that are, or once were, the committed `C` at a strictly increasing generation. An unvalidated, uncommitted or superseded candidate can never enter `A`. | D1.1 to D1.4 |

D1.5 is the invariant [TH-21](../../../BACKLOG.md#th-21) and [TH-22](../../../BACKLOG.md#th-22) later have to test, and TADR-004 line 46 already requires that test at every boundary named below.

### Where the stages sit in the runtime seam

The four stages run entirely inside the non-advancing control drain (HF-04a line 24). They advance no gameplay time, consume no input edge and commit no tick.

| Ordering rule | Statement | Source |
| --- | --- | --- |
| SEAM-1 | A candidate is staged only from the values of a complete published tick. P6 is the only phase that commits a tick and publishes identified committed results; a partial tick supplies nothing. | HF-04a lines 67 and 172 |
| SEAM-2 | Session reads and accepts the completed result batches, then settles or retains the identified transition, after O1 and O2 and with ticking held by O3. | HF-04a lines 108, 87 to 89 and 173 |
| SEAM-3 | No lifecycle callback awards a completion reward and no `_exit_tree` path settles one. The transition is Session's, not the outgoing scene's. | HF-04a lines 48 and 106 |
| SEAM-4 | The pending transition lives in Session's `PendingTransition` before the outgoing encounter is discarded, and survives replacement with `RunState` and `ProfileState`. | HF-04a lines 81 and 106 |
| SEAM-5 | The persistence result arrives as F-ASYNC. Session reads it through a listed edge and validates its lifetime and identity before any explicit control transition; a stale completion arriving after teardown is rejected and never routed into a reward replay. | HF-04a lines 50 and 176 |
| SEAM-6 | Playable state is restored through O4 only after the transition's identity is in `A`. An unresolved critical write blocks playable replacement. | HF-04a lines 108, 113 and 178 |
| SEAM-7 | Pausing the dashboard is not a checkpoint and stages nothing. | BIBLE line 584 |

### Transition A: level completion

The candidate carries the completed level's checkpoint: `run.checkpoint.next_entrance` advanced to the entrance after the completed level, together with the checkpoint fields that changed during the level — `run.checkpoint.route`, `run.checkpoint.generation_decisions`, `run.checkpoint.rng_state`, `run.checkpoint.offered_choices`, `run.checkpoint.resolved_rewards`, `run.checkpoint.equipment.owned`, `run.checkpoint.equipment.equipped`, the build-selection fields and `run.checkpoint.device_carry_over`. `run.lifecycle.revival_spent` and `run.lifecycle.terminal` are carried forward unchanged. Transition A also covers the destination offer that the completed level's world transition opens (BIBLE line 580). When the generator runs in the same accepted-results batch as the completion, the offer's `run.checkpoint.offered_choices[]` entry rides in the candidate above. When it runs after that completion has already committed, the offer commits as a second Transition A write whose only aggregate change is that entry, with `chosen_option_id` null and `run.checkpoint.next_entrance` unchanged; it is still level-completion content, because the offer is the completed level's exit and no other field moves. Answering the offer is Transition B. The four stages below are re-argued for that offer-only path in place.

1. **Stage.** Build the candidate from the accepted results of the level's last complete tick (SEAM-1, SEAM-2). *Before:* `C` is generation `G`, `run.checkpoint.next_entrance` is the previous entrance and `run.checkpoint` is null when no level has completed yet; `L` holds the completion in `PendingTransition`; the player is not yet at the next level. *After:* `C` unchanged; `S` holds the candidate; nothing the player can observe has become durable. *Offer-only path:* Persistence stages a candidate whose only change is the new `run.checkpoint.offered_choices[]` entry carrying the options the generator actually produced and a null `chosen_option_id`. *Before:* `C` is generation `G` with no entry for this offer; the destinations may be on screen but nothing about them is durable; `L` holds the world transition. *After:* `C` unchanged; `S` holds the candidate; a restore at this instant re-presents the world transition.
2. **Validate.** In addition to the common checks: `run.checkpoint.route` sequences ascend from 0 with no gaps; every `run.checkpoint.route[].offer_id` that is non-null names a committed or candidate `run.checkpoint.offered_choices[].offer_id`; every `run.checkpoint.equipment.equipped[].instance_id` names an entry in `run.checkpoint.equipment.owned`; no `run.checkpoint.resolved_rewards[].settlement_id` committed at `G` is absent from the candidate; no committed `run.checkpoint.offered_choices[]` entry has different `option_ids` in the candidate. *Before and after:* `C` unchanged at `G`; the candidate becomes eligible or is rejected and preserved. *Offer-only path:* the common checks plus: the new `run.checkpoint.offered_choices[].offer_id` is absent from the committed entries; every `run.checkpoint.offered_choices[].option_ids` value resolves under `content_revision`; `chosen_option_id` is null while the offer is open; no committed offer's `option_ids` differ; no committed `run.checkpoint.resolved_rewards[].settlement_id` and no committed `run.checkpoint.route` step is dropped; and `run.checkpoint.next_entrance` is unchanged, because presenting an offer is not taking it. *Before and after:* `C` unchanged at `G`; the candidate becomes eligible or is rejected and preserved.
3. **Commit.** *Before:* `C` at `G` with the previous entrance. *After:* `C` at `G+1` with the completed level's checkpoint and the new `run.checkpoint.next_entrance`. A restore from this instant onward resumes at the next entrance with the build and the resolved rewards intact (BIBLE line 584). *Offer-only path:* *Before:* `C` at `G` with no entry for this offer. *After:* `C` at `G+1` carrying the destinations actually generated, with `run.checkpoint.next_entrance` still the entrance the completed level reached. From this instant a restore replays the same two destinations by value and consults no generator (HF-07a rule 4 at line 60), which is the whole content of N3.
4. **Acknowledge.** *Before:* `C` at `G+1`, `T'` not in `A`, Session still holding the completion and the encounter still held by O3. *After:* `T'` in `A`; Session releases the completion, may retire the outgoing encounter and may restore play at the next level through O4 (SEAM-6). A hold at any stage keeps the player in the held state with a recoverable save error and never presents the level as banked. *Offer-only path:* *Before:* `C` at `G+1`, `T'` not in `A`, Session holding the world transition. *After:* `T'` in `A`; only then is the offer banked and answerable through Transition B. A hold at stage 1 or 2 leaves no stored offer, so a restore re-presents the world transition and may generate the offer afresh; N3 binds only an offer the committed record already holds. A hold at stage 3 or 4 leaves the offer durable but unreleased, and the world transition stays held with a recoverable save error rather than presenting an unproven offer as answerable.

### Transition B: reward and offer resolution

Reward settlement and its checkpoint and profile effects commit together in one transaction (TADR-004 line 28). One settlement is never split across two transactions. A single transaction may carry a completed level and one or more settlements; every rule below is stated per `run.checkpoint.resolved_rewards[].settlement_id`, so it holds whether a settlement rides with Transition A or commits on its own.

1. **Stage.** Build the candidate containing the new `run.checkpoint.resolved_rewards[]` entry with its `settlement_id`, its `resolved_ids` as the domain IDs the settlement actually resolved to, and its `instance_ids` naming the `run.checkpoint.equipment.owned[].instance_id` values it created, together with those owned entries and any `profile.discoveries`, `profile.recipes` or `profile.unlocks` entry the same settlement caused. When an offer is being answered, the candidate also sets that offer's `run.checkpoint.offered_choices[].chosen_option_id`. *Before:* `C` at `G` without the `settlement_id`; the player has seen the outcome presented but it is not banked. *After:* `C` unchanged; `S` holds the candidate.
2. **Validate.** In addition to the common checks: the new `settlement_id` is not already present in the committed `run.checkpoint.resolved_rewards`; every `instance_ids` value names an owned entry in the same candidate and appears in no other settlement; every `resolved_ids` value resolves under `content_revision`; a non-null `chosen_option_id` is a member of that offer's stored `option_ids` and the offer's `option_ids` are byte-identical to the committed ones; and `profile.discoveries`, `profile.recipes` and `profile.unlocks` remain unique sets that only grow. *Before and after:* `C` unchanged at `G`.
3. **Commit.** *Before:* `C` at `G`, settlement unrecorded. *After:* `C` at `G+1` carrying the settlement, the instances it created, the chosen option and the profile entries, all in the same generation. From this instant a reload cannot duplicate the reward, because the `settlement_id` is present, and cannot reroll it, because the outcome is stored rather than recomputed (BIBLE line 584; HF-05 line 58; HF-07a rule 4 at line 60).
4. **Acknowledge.** *Before:* `C` at `G+1`, `T'` not in `A`, Session holding the settlement pending. *After:* `T'` in `A`; Session releases it and the reward may be presented as banked and equipped. Presentation's cue-consumption state never acknowledges a settlement, and a repeated read of the same result batch cannot settle it twice (HF-04a line 81).

### Transition C: revival use

The first lethal defeat of a run consumes the one standard revival (BIBLE line 582). The candidate sets `run.lifecycle.revival_spent` true and changes nothing else, so `run.checkpoint` may be byte-identical to the committed one. A new aggregate commits even then (TADR-004 line 30).

1. **Stage.** *Before:* `C` at `G` with `run.lifecycle.revival_spent` false; the player is in the defeat moment and gameplay is held; no revived state has been presented. *After:* `C` unchanged; `S` holds the candidate whose only difference from `C` is the flag and the envelope identity.
2. **Validate.** In addition to the common checks: `run.lifecycle.revival_spent` is true; `run.lifecycle.terminal` is false in both the committed record and the candidate, because a terminal run has no revival to spend; `run.run_id` is unchanged; and no checkpoint array has lost a member. A candidate whose `revival_spent` is false while the committed value is true is rejected outright, which is the monotonicity gate N4 depends on. *Before and after:* `C` unchanged at `G`.
3. **Commit.** *Before:* `C` at `G`, revival available. *After:* `C` at `G+1`, `run.lifecycle.revival_spent` true. From this instant no restore can refill the revival, and an older generation offering `revival_spent` false is refused because its generation is not greater (D1.4; TADR-004 line 40; HF-03a line 58).
4. **Acknowledge.** *Before:* `C` at `G+1`, `T'` not in `A`. *After:* `T'` in `A`, and only then may play resume into the revived encounter through O4. TADR-004 line 32 forbids continuing through a completed revival transition whose durability is unknown, so a hold here keeps the defeat moment held with a recoverable error rather than reviving the player on an unproven write.

The health and placement the player resumes with are encounter values under every Q-P16 candidate answer and appear in no field (HF-07a line 159 and scenario S5). A companion cannot create a second revival and no field can express one (TADR-004 line 30; HF-07a line 146).

### Transition D: terminal settlement

A death after the revival is spent closes the run (BIBLE line 582). The candidate sets `run.lifecycle.terminal` true.

1. **Stage.** *Before:* `C` at `G` with `run.lifecycle.terminal` false; gameplay held at the fatal moment; no results screen presented and no new run startable. *After:* `C` unchanged; `S` holds the candidate.
2. **Validate.** In addition to the common checks: `run.lifecycle.terminal` is true; `run` is an object and `run.run_id` is unchanged, because a closed run stays present and is never removed by dropping the key (HF-07a line 80); `run.lifecycle.revival_spent` is not weakened; and `profile.discoveries`, `profile.recipes` and `profile.unlocks` are supersets of the committed sets, because permanent discoveries, learned recipes, options and challenges survive defeat (BIBLE line 586; D26). *Before and after:* `C` unchanged at `G`.
3. **Commit.** *Before:* `C` at `G`, run playable. *After:* `C` at `G+1`, `run.lifecycle.terminal` true. Playability is derived from the flag and is false from this instant (HF-07a rule 2 at line 58). A checkpoint predating the fact cannot override it (TADR-004 line 30; HF-03a line 58).
4. **Acknowledge.** *Before:* `C` at `G+1`, `T'` not in `A`. *After:* `T'` in `A`; only then may another playable state resume — the results screen, the yard or a new run. TADR-004 line 30 requires the closed status to commit before another playable state can resume, and line 32 forbids continuing through a terminal transition whose durability is unknown, so a hold keeps the fatal moment held rather than starting a run that a restore could contradict.

### The nonduplication invariants

| ID | Invariant | Mechanism in `C` | Source |
| --- | --- | --- | --- |
| N1 | A settlement resolves once. A `run.checkpoint.resolved_rewards[].settlement_id` present in `C` is never applied again. | Presence of the `settlement_id` in the committed array, checked at validate. | BIBLE line 584; TADR-004 line 28; HF-07a line 123 |
| N2 | A settlement grants its instances once. No two owned entries are created by one settlement twice. | `run.checkpoint.resolved_rewards[].instance_ids` ties a settlement to the `run.checkpoint.equipment.owned[].instance_id` values it produced. | BIBLE line 465; HF-07a lines 117 and 126 |
| N3 | A committed offer is stable. ### Two decisions this card owns

**Acknowledgement leaves no durable trace.** [The S0-08 page](../proofs/S0-08-save-evidence.md) line 66 records "rename completed, acknowledge not yet recorded" as the one interruption row with no fixture, because that owner's acknowledgement is in-memory, and line 70 hands the decision to this card. The decision is that `A` is live only and the aggregate gains no acknowledgement field. The reasons: HF-07a line 175 fixes the envelope at exactly six keys and lines 177 to 185 reject a durability, commit or write-reason key, so a durable acknowledgement would require an amendment to an admitted contract rather than an addition here; and it is unnecessary, because a committed record is durable by being the record a restore reads, while a candidate that never committed is not. The consequence is stated rather than hidden: **a crash between commit and acknowledge is indistinguishable on storage from a crash after acknowledge.** That is safe in the only direction that matters. In both cases `C` already carries the transition, so a restore sees the completed level, the settled reward, the spent revival or the closed run; and re-delivering the same transaction converges by N6 rather than writing a second generation. What is *not* safe, and what the hold rule and SEAM-6 exist to prevent, is the opposite order: presenting a transition as done, or resuming playable state, before the commit that carries it. [HF-08](../../../BACKLOG.md#hf-08) owns what recovery does with a preserved candidate; this decision adds no input to that question.

**A preferences write is not a gameplay commit.** HF-07a line 187 hands this to this card and to HF-08. The decision is that the preferences record uses the same four stages over its own document and its own `preferences.schema_version`, and nothing else. It has no `generation` and no `transaction_id` (HF-07a line 187), so it has no convergence identity, no ordering against the aggregate and no place in `A`. It carries no lifecycle fact and no gameplay progress (HF-07a rule 6 at line 62), so a failed preferences write is not a failed critical write under TADR-004 line 32: it holds the preference change and shows a recoverable error, it must not report the preference as saved, and it never holds a gameplay transition. Symmetrically, no gameplay transition waits on a preferences write. This is the separation TADR-004 line 24 requires, and it adds no field to either document.

## Unresolved questions

- [Q-P16](../../../BACKLOG.md#q-p16) (revival and unfinished-level interruption) is unanswered in both halves. This section adopts no candidate and no proposal. - [Q-E09](../../../BACKLOG.md#q-e09) (permanent discovery write timing) is `proposed` with its product half unanswered. It decides *when* a `profile.discoveries`, `profile.recipes` or `profile.unlocks` entry commits, never what is stored. Under the immediate answer the entry commits in a transaction whose only aggregate change is the profile array; under the deferred answer it rides in the completed-level or terminal transaction. Both use the same four stages, the same D1 gate and the same N7 invariant, and HF-07a lines 177 to 185 reject a save-side durability-class key under either. The Persistence half of the write-timing protocol has been submitted to the coordinator as a proposal for TRACKING, as the card permits; this section adopts neither it nor any other proposal, and nothing above depends on one. D26 is the same open decision and adopts no storage or write schedule.
- The qualified filesystem protocol is deliberately not chosen here. TADR-004 line 38 states that temporary files, a rename, a checksum or a backup alone do not prove power-loss durability, and S0-08 lines 97 to 101 record that flush and fsync durability, directory-entry durability after rename, non-Linux rename semantics and cross-process single-writer exclusion were not asserted. Write ordering, flush and commit behaviour, recovery evidence and single-writer ownership per target OS remain TADR-004 line 38's later design work.
- What recovery does with a preserved candidate, an ambiguous lifecycle record, a corrupt record or an unsupported newer record is [HF-08](../../../BACKLOG.md#hf-08)'s. This section states only that a failure holds the transition and preserves the source. Versioning and migration are [HF-09](../../../BACKLOG.md#hf-09)'s; D27 leaves the run-checkpoint schema and permanent-profile compatibility to be specified after run state is defined.
- Whether an equipment position exists as a named mount is not settled by any cited source, and this section does not depend on it: every rule above references `run.checkpoint.equipment.owned[].instance_id` and `run.checkpoint.resolved_rewards[].instance_ids`, never a mount. The intermediate aggregate objects `run.checkpoint.build`, `run.checkpoint.equipment` and `run.checkpoint.companion` now carry container rows in HF-07a, so every field path this section names resolves there.
- Numeric thresholds are set nowhere here: no retry count, no timeout, no write budget, no queue capacity and no acceptable hold duration. A dependent implementation needs those specified and qualified separately.
