## Contract

### What migration is, and what it is not

A **migration** turns one committed save document into one newer committed save document, in place of the load that would otherwise have been refused. It is the only mechanism by which a save whose `schema_version` or `content_revision` is not this build's may become playable (TADR-003 line 33; TADR-004 line 34; HF-05 line 52).

A migration is not a repair, a default, a remap or a retirement. TADR-003 line 31 makes missing content and an unsupported version produce a diagnostic rather than a substituted default that changes a saved build; TADR-003 line 41 forbids silently remapping a missing ID, rerolling a saved offer or retiring an old run; HF-05 line 113 makes an observed alternative revision diagnostic context and never an instruction to substitute it. Everything this section refuses to do follows from those three clauses and not from a convention.

Two documents exist and they migrate independently: the aggregate and the preferences record (TADR-004 line 24; HF-07a line 22). The rest of this contract is written for the aggregate. The preferences record's migration is the same machinery on one axis and is stated under "The preferences record migrates alone" below.

### The three inputs, and where each comes from

The compatibility predicate is a function of **a document and a build**, not of a document alone.

| Input | Symbol | Read from | Type and comparison |
| --- | --- | --- | --- |
| Schema version | `S` | The candidate document's envelope, `schema_version` (HF-07a line 78) | `int`, restored through the boundary cast (HF-07a line 46; S0-07 line 45). Integers are ordered, so "older" and "newer" are computable on this axis. |
| Gameplay content revision | `R` | The candidate document's envelope, `content_revision` (HF-07a line 79) | `id-string` with **no assumed numeric ordering** (HF-05 line 23). Nothing about `R` is computable except equality and the declared step edges below. "Newer content" is not a thing this predicate can observe. |
| Catalogue version | `K` | **The build's admitted registry, not the document.** The set of `CatalogueHandle` values `ContentAdmission` currently publishes, each binding one catalogue revision to one gameplay content revision (HF-05 lines 24 and 27) | Compared by looking up a handle for the resolved gameplay content revision and resolving every domain ID the document references with its expected family. |

The aggregate stores no catalogue revision, and it may not: HF-07a line 192 fixes the envelope at exactly six keys and line 200 rejects a second revision field inside `run` or `profile` because a second copy could disagree with the first. A presentation-only catalogue replacement may retain the gameplay content revision after validation establishes identical gameplay definitions (HF-05 line 24), so more than one catalogue revision can satisfy one `R`; that is why the catalogue axis asks whether a handle exists and resolves, not whether a token matches.

**Consequence, stated rather than hidden.** Because `K` is a property of the build, the same bytes can yield different verdicts on two builds or two machines. That is the intended behaviour and it is the reason a reject preserves the source rather than repairing it: TADR-004 line 40 states that unsupported data can remain inspectable without becoming playable, and line 34 requires failure without overwriting the source. A save refused on one build must still be acceptable on the build that has the content.

### The declared step registry

A migration step is a **declaration**, not a discovered transform. The build carries a registry of steps; a step that is not declared does not exist and cannot run.

| Declaration field | Rule |
| --- | --- |
| `step_id` | Opaque, stable, unique in the registry. It is not a domain ID and is never resolved through the catalogue. |
| `axis` | `schema` or `content`. A step changes exactly one axis. |
| `from_schema_version`, `to_schema_version` | `int`. On a `schema` step, `to = from + 1`. On a `content` step, `to = from`. |
| `from_content_revision`, `to_content_revision` | `id-string`. On a `content` step they differ. On a `schema` step they are equal. |
| `adds`, `removes`, `renames` | Field paths in the naming of HF-07a line 24. Empty on a `content` step. A path named here must be named by the admitted field contract for the step's postcondition schema version. HF-07a is that contract for version 1, and no admitted contract exists for any later version, which is a second reason the registry is empty at this base. A field contract for a later version may not introduce a field for derived state; that would amend HF-07a rule 2 rather than extend it, and HF-07a line 281 requires an amendment. |
| `id_bearing` | Which paths in `adds` and `renames` carry `id-string` values. This is what makes the catalogue axis decidable before any step runs. |
| `added_values` | For every required key in `adds`, either one declared constant or one named pure function of values already present in the document. Nothing else. |
| `rationale` | Why the change preserves gameplay meaning, or, when it does not, which gameplay meaning changed and under which Bible or ADR rule. |

Registry well-formedness, checked when the registry is admitted and not at load:

- **At most one step per `from_schema_version`** and **at most one step per `from_content_revision`**. With the `to = from + 1` rule on the schema axis, this makes every chain unique whenever one exists, so the predicate never chooses between paths.
- **The content step graph is acyclic.** A cycle is a declaration defect.
- A registry that violates either rule is not admitted. This is a `ContentAdmissionFailure` (HF-05 line 117) against the registry, not a `ContentReferenceFailure` against a save.

**The added-key rule.** `added_values` may not draw a value from a generator, from an unqualified catalogue lookup, or from a default that changes a saved build (TADR-003 line 31; HF-07a rule 4 at line 63). An added required key whose value cannot be declared as a constant or derived from the document is a step that cannot be declared; the correct outcome is a reject and an explicit product decision, not an invented value.

**The removal rule.** `removes` may not name a path that carries a committed outcome. Validation enforces this through M4, M5, M7 and M8 below rather than through a second list, so the rule cannot drift from the invariants.

### The compatibility predicate

The predicate evaluates three axes in this order and stops at the first that does not pass. The order is not a preference. A document whose field layout this build does not understand cannot have its fields addressed at all, so the schema axis must settle first; an ID cannot be resolved without knowing which revision resolves it, so the content axis must settle before the catalogue axis.

**Schema axis `SA`**, on `S` against this build's current version `V` and the registry:

| `SA` | Condition |
| --- | --- |
| `current` | `S == V`. |
| `step` | `S < V` and the registry declares a step from every version in `S, S+1, …, V-1`. The chain is unique by the registry rules. |
| `unsupported-older` | `S < V` and some version in that range has no declared step. |
| `newer` | `S > V`. |
| `malformed` | `schema_version` is absent, is not a number, or is not an integer value (HF-07a lines 56 and 78; the boundary cast at S0-07 line 45). |

**Content axis `CA`**, on `R` against the build's admitted gameplay content revisions and the registry:

| `CA` | Condition |
| --- | --- |
| `pinned` | Exactly one admitted gameplay content revision equals `R`. Whether a catalogue handle for it exists and resolves is the catalogue axis's question, not this one. |
| `step` | `R` is not admitted, and the registry declares a unique content chain from `R` to an admitted revision `R'`. |
| `missing` | `R` is not admitted and no chain leads to an admitted revision. |
| `ambiguous` | More than one admitted catalogue binds `R` to a different gameplay meaning, so the saved pair cannot resolve to one meaning (HF-05 lines 24 and 27). |
| `malformed` | `content_revision` is absent or is not a nonempty string (HF-07a lines 56 and 79; HF-05 line 18). |

**Catalogue axis `KA`**, on the resolved revision — `R` under `CA=pinned`, `R'` under `CA=step` — and on the document's domain IDs **as the declared schema chain leaves them**:

| `KA` | Condition |
| --- | --- |
| `complete` | A `CatalogueHandle` binds a catalogue revision to the resolved gameplay content revision, and every domain ID the document then carries resolves with its expected family (HF-05 lines 27 and 51). |
| `no-handle` | No admitted catalogue binds that gameplay content revision. |
| `ambiguous` | More than one admitted catalogue binds it with gameplay definitions validation has not established as identical (HF-05 line 24). |
| `missing-id` | A required domain ID does not resolve under that pair. |
| `wrong-family` | A domain ID resolves to a definition of the wrong family. |

`KA` is computable before any step runs. On the content axis that follows from **M9**: no step rewrites a domain ID, so the ID set is invariant under content steps. On the schema axis it follows from the declaration: `adds`, `removes`, `renames` and `id_bearing` say exactly which paths carry IDs after the chain. This is the **decidability property**: the predicate returns its verdict from declarations alone, with nothing staged, nothing written and the source untouched.

One code in HF-05's closed set at line 105 is not reachable from the predicate: `incompatible_revision` is not a verdict about a document, it is the verdict on a **produced** document, raised when a step's actual output fails the per-step validation in "Each step validated before the next" below. Rows P1 to P14 decide from declarations; `incompatible_revision` is what catches a step whose implementation disagrees with its declaration.

Every reject row shares the same three consequences and no others:

1. **Nothing is written.** No candidate is staged, no generation advances, the committed record is byte-identical afterwards (TADR-004 line 34; M2).
2. **The affected operation is held**, carried as `held_operation` on the diagnostic (HF-05 line 114) with `operation` set to `restore` or `migration` as the caller supplied it (HF-05 line 106).
3. **The source stays inspectable.** TADR-004 line 40 permits unsupported data to remain inspectable without becoming playable. What the player is shown, whether a preserved record is ever repaired and what recovery does next are HF-08's (HF-07b line 307), not this contract's.

The `available_revision` field may carry an observed alternative as diagnostic context and is never an instruction to substitute it (HF-05 line 113). No reject row may be resolved by choosing a different revision, a nearest definition or a newer catalogue.

### Chaining: ordered single-step migrations

A chain is the ordered list of declared steps the predicate resolved: the schema steps from `S` to `V` in ascending order, then the content steps from `R` to `R'` in declared order. The card's item 1b is satisfied by five properties of that list.

**Working area.** The chain runs in a working area that is not storage: no intermediate is staged, no intermediate is a member of the staged candidate set `S` of HF-07b line 27, and no intermediate is readable as gameplay state. Only the final document leaves the working area.

**One commit for the whole chain.** A chain of `k` steps produces exactly one candidate and, on success, exactly one new generation `G+1`. TADR-004 line 34 preserves the original "until the new generation commits", singular; HF-07b D1.4 at line 55 requires a strictly greater generation, so committing every intermediate would burn `k` generations and — worse — would make a partial chain durable. It does not happen here.

**Ordering between the axes.** Schema steps run first, then content steps. A content step addresses fields by their HF-07a path (HF-07a line 24) to check that every `(content_revision, ID)` pair still resolves (HF-05 line 27); it can only do that once the document is at this build's layout. A registry that declared a content step operating on a superseded layout would be declaring a step whose `from_schema_version` is not `V`, which the content-step rule forbids.

**Handles held on both sides.** Before the first step, `ContentAdmission` retains the source revision's handle and the target revision's handle, and both stay retained for the whole chain (HF-05 line 121). The source pin remains authoritative until the migrated transaction is acknowledged; edge E07 preserves the source binding while the transition is pending and edge E06 establishes the target binding afterwards (HF-05 lines 85, 86 and 121).

**A migration is not a run start.** M7 keeps `run.run_id` unchanged, so the migrated candidate is always compared with an earlier state of the same run: HF-07b line 38 scopes the common validator's checks on a run's own facts by `run.run_id`, and those scoped comparisons therefore apply to a migrated candidate in full. A candidate carrying a different `run.run_id` is a Transition S candidate and is admitted only under that transition's admission rule, a committed `run` that is null or terminal (HF-07b lines 112 and 116); no chain in this section can produce one, and none of the rules above stages, orders or authorizes a run start. A migrated save whose run is closed may then start a new run through Transition S, for a won run and a lost run alike, because the admission fact is `run.lifecycle.terminal` and not `run.lifecycle.outcome`. That start is a separate transition with its own candidate and its own generation, and this section neither performs it nor decides when it is allowed.

**The commit.** The final document is handed to the HF-07b protocol as one ordinary candidate and takes all four stages without exception (HF-07b line 35):

| Stage | What the migration does | Source at this instant |
| --- | --- | --- |
| 1 Stage | Persistence builds the candidate from the chain's output, sets `generation` to the committed generation plus one, sets a fresh `transaction_id`, and serialises it with the array order HF-07a rule 5 fixes (HF-07b line 37). | `C` is the source at `G`/`T`, byte-identical. |
| 2 Validate | Persistence re-reads the candidate bytes from storage, never the working-area object, and applies HF-07b's common checks in full (HF-07b lines 38 and 54): every required key present and correctly typed, `schema_version` supported, every domain ID resolvable as the pair of `content_revision` and that ID, `generation` strictly greater, and — because the candidate keeps the source's `run.run_id` and is therefore compared inside its own run — `run.lifecycle.revival_spent` and `run.lifecycle.terminal` not weaker, `run.lifecycle.outcome` null exactly when `terminal` is false and never rewritten once non-null, and `run` still present under that same identity. | `C` unchanged. A rejected candidate is preserved and never overwrites the source (HF-07b line 38). |
| 3 Commit | The validated candidate replaces the committed record through the qualified filesystem protocol TADR-004 line 28 requires (HF-07b line 39). | `C` becomes `G+1`/`T'` and now carries this build's `schema_version` and the target `content_revision`. |
| 4 Acknowledge | Only after commit returns success is `T'` recorded as durable (HF-07b line 40). | Only now may Session install the new run binding through E06 and resume (HF-05 lines 85 and 121; HF-07b SEAM-6 at line 71). |

**A failure anywhere abandons the chain.** A step that fails its validation, or a candidate that fails stage 2, or a commit that fails at stage 3, leaves `C` at `G`/`T` and the transition held with a recoverable save error (TADR-004 line 32; HF-07b line 42). The partial work in the working area is discarded because it was never durable. A failure at stage 3 leaves a preserved candidate whose resolution is HF-08's (HF-07b line 42), and a failure to acknowledge after a successful commit leaves `C` at `G+1`/`T'` and holds the restore, which is the safe direction (HF-07b line 173).

**An accept commits nothing.** Row P1 performs a read, and a read is not a durable transition. No generation advances, no `transaction_id` is issued and the acknowledgement set is untouched. A build that bumped the generation on every compatible load would make the generation an access counter rather than the ordering TADR-004 line 30 relies on.

### The invariants

| ID | Invariant | Why it cannot be relaxed |
| --- | --- | --- |
| M1 | **One commit per migration.** A chain of any length produces exactly one candidate and exactly one new generation. No intermediate is staged, committed, acknowledged or readable as gameplay state. | TADR-004 line 34 preserves the original until *the* new generation commits; HF-07b D1.4 at line 55 makes generations strictly increasing. |
| M2 | **The source is preserved.** Until the migrated `transaction_id` is acknowledged, the committed record is the source, byte-identical. A reject writes nothing at all. | TADR-004 lines 34 and 40; HF-07b line 38 and the hold rule at line 42. |
| M3 | **Determinism.** A step is a pure function of its input document. Re-running a chain on the same source produces the same content; only the envelope's `transaction_id` differs. | HF-07a rule 4 at line 63 forbids a seed replacing a stored outcome; rule 5 at line 64 fixes array order; S0-07 line 45 records byte-for-byte re-serialisation. |
| M4 | **No reroll.** No step alters a committed offer's `option_ids` or `chosen_option_id`, and no step consults a generator. `run.checkpoint.rng_state` is carried by value and never used to recompute a stored outcome. | BIBLE lines 580 and 584; TADR-003 line 41; HF-05 line 58; HF-07b N3 at line 129. |
| M5 | **No loss of knowledge.** `profile.discoveries`, `profile.recipes` and `profile.unlocks` are supersets across every step and across the whole chain. On a reject they are untouched, because nothing is written. | BIBLE lines 462, 463 and 586; TADR-004 line 26; HF-07b N7 at line 133. |
| M6 | **No added active effect.** No step writes a field outside the admitted field contract for its postcondition schema version — HF-07a's seventy at version 1 — and HF-07a rule 2 at line 61 gives derived state no field at all. There is no field in which an active effect, a derived stat, a recipe bonus or a playability flag could be written, and a later field contract may not create one without amending that rule. | BIBLE lines 465, 552 and 564; HF-05 line 56; HF-07a rule 2, line 199 and line 280. |
| M7 | **Lifecycle monotonicity.** `revival_spent` and `terminal` are never weakened by a step; `outcome` is never rewritten and stays null exactly when `terminal` is false, so a migration of a closed run keeps it closed and keeps the record of which of the two ways closed it; `run.run_id` is unchanged, so a migration is never a run start; `run` stays an object once it is one, so a closed run cannot be reopened by a migration dropping a key. | BIBLE lines 582 and 584; TADR-004 line 30 and § Amendment 2026-09-16 line 52; HF-07a lines 83 and 176; HF-07b N4 and N5. |
| M8 | **No settlement change.** The `settlement_id` set and each entry's `resolved_ids` and `instance_ids` are unchanged, so a migration can neither duplicate nor drop a resolved reward. | BIBLE lines 465 and 584; TADR-004 line 28; HF-07b N1 and N2. |
| M9 | **No ID rewriting.** No step maps a domain ID to another token. A definition that no longer exists produces `missing_id` and a reject, never a substitution. | TADR-003 lines 25 and 41; HF-05 line 18; HF-07a rule 3 at line 62. |
| M10 | **Separation.** The aggregate and the preferences record migrate independently. A gameplay migration never reads or writes the preferences record, a preferences migration never reads or writes the aggregate, and neither waits on the other. | TADR-004 line 24; HF-07a rule 6 at line 65 and line 204; HF-07b line 175. |

M6 deserves the sharper statement, because it is the one negative the card names that is not enforced by a comparison. A migration cannot add an active effect **because the aggregate has nowhere to put one.** `EffectiveBuild`, active recipe bonuses, derived stats, compatibility outcomes, current health and playability are rebuilt from the restored selections and are named in no field (HF-07a rule 2 at line 61; HF-05 line 56; HF-06b rule 6 at line 36). The most a step could do at version 1 is add a member to `node_keys` or to `equipped`, and G11 and G12 reject both. Whatever effects the player has after a migration are the effects the migrated selections rebuild, once each, under the target revision — which is exactly what BIBLE lines 552 and 564 require of an ordinary reload.

**`run.start`, `run.lifecycle.outcome` and `run.interruption` migrate by value.** HF-07a line 26 splits a run's own facts between `run.start.*`, written once by the run-start transition and never rewritten, and `run.checkpoint.*`, produced by completing a level, so a started run carries `run.start` while `run.checkpoint` is still null. A step carries `run.start.character_id` (HF-07a line 113), `run.start.entrance_id` (line 114) and the `run.start.rng_state` entries (lines 115 to 117) by value, exactly as it carries any other stored outcome: the first two are domain IDs that M9 forbids rewriting, and the generator state is stored state that rule 4 already forbids using to recompute anything. `run.lifecycle.outcome` (HF-07a line 176) is the enumerated `won` or `lost` record of how a closed run closed, and G8 carries it under the same monotonicity that carries `terminal`. `run.interruption` (HF-07a line 104) sits beside the checkpoint rather than inside it, so a step reads and copies it whether or not `run.checkpoint` is null. None of these is derived state and none is recomputed; a step may move one only by a declared `renames` that G4 compares against the admitted field contract, and at version 1 no such contract and no such step exists.

### The preferences record migrates alone

The preferences record carries `preferences.schema_version` and the five settings, no `content_revision`, no `generation` and no `transaction_id` (HF-07a lines 184 to 188 and 204). Its migration is therefore the same machinery with two axes removed:

- The predicate degenerates to the **schema axis only**. Rows P1, P2, P5, P6 and P7 apply verbatim with `S` read from `preferences.schema_version`; rows P3, P4 and P8 to P14 cannot arise, because the record names no authored content (HF-07a rule 6 at line 65).
- A chain of preferences steps commits through the four stages over its own document (HF-07b line 175). It has no convergence identity, no ordering against the aggregate and no place in the acknowledgement set.
- A failed or rejected preferences migration **holds the preference change and never holds a gameplay transition** (HF-07b line 175). A save that would not open because the settings file came from a newer build is the failure mode this rule exists to prevent.
- `preferences.schema_version` exists precisely so the settings can migrate without touching gameplay progress (HF-07a line 184), so a preferences step may never write a field of the aggregate, and M10 makes the converse true as well.

What the interface presents after a rejected preferences record, and whether the player is offered defaults, is HF-08's and the interface contract's. This section fixes only that the rejected record is preserved, not overwritten, and not load-bearing for gameplay.
