## Contract

### What this section fixes

It fixes ten run-loop states, what each carries and who owns it; the complete set of module interfaces the loop uses and the edge each travels on; the order in which one loop turn runs; twelve edge cases and nine failure modes stated as required behaviour; and thirty-one tunable parameters, each either carrying a source line or gated on a question ID. It fixes no number that no cited source states.

It is not a runtime. A state named here has never been entered, an interface named here has never been called, and no engine, browser or build ran for it.

### Owned data

The loop reads and writes exactly the records the carried-state table assigns, through the interfaces above, and nothing else.

1. **Session writes `RunState`, `ProfileState`, `EffectiveBuild`, `SessionControl` and `PendingTransition`.** It settles each accepted reward, offer and route result once, including removal of the old effects when a selection changes (HF-03a line 57). It never writes a durable record and never mutates another owner's record.
2. **Encounter writes its five records and no other.** It receives the build, the run facts it needs, the complete definition set and a seed as values at `initialize_encounter`; it holds no writable `RunState` alias (HF-03a line 46). Its records end at `retire`.
3. **CollisionQueries writes its two records.** They are encounter-bound and discarded with the world. Encounter alone commits the authoritative gameplay pose (HF-03a line 47).
4. **ContentAdmission writes its two records.** The run's pin selects a revision without modifying the catalogue, and a replacement candidate never edits cached Resources a live run still references (HF-03a line 48).
5. **Persistence writes `SaveTransactionState`, `DurableAggregate`, `PreferencesRecord` and `RecoveryState`, and it alone stages or replaces them and writes their files** (HF-03a line 49). Session requests a transition on D04 and supplies the accepted inputs; Persistence builds the candidate, validates it, commits it and acknowledges it (HF-07b lines 37 to 40). HF-10 required fix RF-6 at line 64 recorded the one admitted scenario step that read otherwise; FR-01 applied it, and HF-07b line 207 now names Persistence as the stager on Session's accepted results.
6. **InputAdapter writes its two records**; clearing physical input cannot mutate a prepared action, a pause state, a save or the run (HF-03a line 50).
7. **Presentation writes its two records from published values.** View bindings are not actor ownership; cue consumption settles no reward and acknowledges no transition (HF-03a line 51; HF-07b line 90).

### One seam closed and one stated and not decided

**Seam 1, closed: run start and the terminal handoff.** Run start is settled by [FR-02](../../../BACKLOG.md#fr-02)'s Transition S and by [Q-P40](../../../BACKLOG.md#q-p40)'s recorded resolution, and this section reads that result rather than restating a gap. A run begins with a durable transition of its own: the candidate carries a new `run.run_id`, `run.start` populated with the character, the entrance and the generator streams the run begins from, a null `run.checkpoint`, a null `run.interruption` and `revival_spent`, `terminal` and `outcome` false or null, and it is admitted only when the committed `run` is null or the committed `run.lifecycle.terminal` is true (HF-07b lines 114, 116). `start_run` and `restore_run` remain Session commands (HF-04a line 131); what changed is that the durable record of a start now exists before a level is banked, so `run.start.entrance_id` is the committed resume position until `run.checkpoint` stops being null (HF-07a line 114). The terminal state hands off to Transition D, which closes a run both ways: the candidate sets `run.lifecycle.terminal` true with `run.lifecycle.outcome` `lost` on the defeat path or `won` on the victory path, the closed status commits before any other playable state exists, and only the acknowledgement releases the results surface, the yard or a new run through Transition S (HF-07b lines 105 to 110). [FR-01](../../../BACKLOG.md#fr-01) applied the HF-10 required fixes in the same integration, so HF-07b line 207 names Persistence as C1.1's stager and lines 257 and 259 carry Transition A's offer-only path; both cards are admitted and neither is concurrent work. What was open at that revision is now settled and this section reads the result rather than deciding it: [Q-P39](../../../BACKLOG.md#q-p39) resolved at TRACKING EV-0247 so that a run started while the committed run is alive abandons it as a defeat, which is RL8's Transition D with `outcome` `lost` and then Transition S, two transactions in two generations, and [Q-P16](../../../BACKLOG.md#q-p16) resolved at the same event so that an unfinished level leaves `run.interruption` null and the loop resumes at the last completed level. Every HF-07a and HF-07b line number cited here is a line in the bytes hashed in the Sources and re-fires if either section changes again.

The third item of the same seam closes with it: how a **successful** run reaches a closed durable state. BIBLE line 582 states that a final encounter completes a successful run and leaves its placement to Q-P12. Transition D is that transition: the same four stages, the same gates and the same invariants as the defeat path, with `run.lifecycle.outcome` set to `won` in the generation that sets `terminal` true, with `run.lifecycle.revival_spent` free to hold either value because a run can be won with the revival spent or unspent, and with what a won run then presents left as a product matter no stage performs (HF-07b lines 105, 108, 109). Transition S's admission rule then reads a won run as terminal exactly as it reads a lost one (HF-07b line 116). Which encounter is final stays Q-P12's, and this section invents neither a transition nor a field for it.
