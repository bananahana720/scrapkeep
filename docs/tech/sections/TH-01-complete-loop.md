## Contract

### What this section fixes

It fixes ten run-loop states, what each carries and who owns it; the complete set of module interfaces the loop uses and the edge each travels on; the order in which one loop turn runs; twelve edge cases and nine failure modes stated as required behaviour; and thirty-one tunable parameters, each either carrying a source line or gated on a question ID. It fixes no number that no cited source states.

It is not a runtime. A state named here has never been entered, an interface named here has never been called, and no engine, browser or build ran for it.

### Owned data

The loop reads and writes exactly the records the carried-state table assigns, through the interfaces above, and nothing else.

1. **Session writes `RunState`, `ProfileState`, `EffectiveBuild`, `SessionControl` and `PendingTransition`.** It settles each accepted reward, offer and route result once, including removal of the old effects when a selection changes (HF-03a line 57). It never writes a durable record and never mutates another owner's record.
2. **Encounter writes its five records and no other.** It receives the build, the run facts it needs, the complete definition set and a seed as values at `initialize_encounter`; it holds no writable `RunState` alias (HF-03a line 46). Its records end at `retire`.
3. **CollisionQueries writes its two records.** They are encounter-bound and discarded with the world. Encounter alone commits the authoritative gameplay pose (HF-03a line 47).
4. **ContentAdmission writes its two records.** The run's pin selects a revision without modifying the catalogue, and a replacement candidate never edits cached Resources a live run still references (HF-03a line 48).
5. **Persistence writes `SaveTransactionState`, `DurableAggregate`, `PreferencesRecord` and `RecoveryState`, and it alone stages or replaces them and writes their files** (HF-03a line 49). Session requests a transition on D04 and supplies the accepted inputs; Persistence builds the candidate, validates it, commits it and acknowledges it (HF-07b lines 36 to 39). **Rebuilt-each-run power.** Within a run the player builds combat power; at run end that power resets and the discoveries do not. Every character has four character-specific binary trees, each a root that forks twice again to eight endpoints, with one connected root-to-endpoint lineage selected per slot (BIBLE line 529). None is chosen here.

**Permanent discoveries.** Permanent discoveries, learned recipes, options and challenges survive defeat (BIBLE line 586; docs/DISCOVERY.md line 33). In the durable record they are sets that only grow: a repeated commit adds no second copy and grants no bonus, because the bonus is rebuilt rather than stored (HF-07b line 119). A discovered recipe's effect still requires the eligible current-run build again, and respeccing out of the combination removes the derived bonus while retaining the knowledge (BIBLE lines 562, 564). Transition D validates that the three profile sets are supersets of the committed ones, which is how the loop's terminal state preserves them (HF-07b line 105). Which facts create a discovery is Q-P37; when a discovery fact commits is Q-E09, whose product half is unanswered and whose two poles both use the same four stages and the same N7 invariant (HF-07b line 261).

### Two seams stated and not decided

**Seam 1: run start and the terminal handoff.** The terminal state of this loop hands off to Transition D exactly as admitted at this base: the candidate sets the run's terminal lifecycle fact, the closed status commits before any other playable state exists, and only the acknowledgement releases the results surface, the yard or a new run (HF-07b lines 100 to 107). Run start has no such transition at this base. `start_run` and `restore_run` are Session commands (HF-04a line 131), and `run.checkpoint` is null until the run's first level completes (HF-07a line 99), so nothing durable records that a run began until a level is banked. The run-start transition [FR-02](../../../BACKLOG.md#fr-02) defines closes that gap and splits the initial-run facts out of the checkpoint. This section names that handoff, specifies no validate rule for it, states no field it introduces, and decides nothing about Q-P39, whose live-run case FR-02 is itself required to leave open. Related and equally not repaired here: HF-10 required fix RF-6 at line 64 records that HF-07b's scenario step C1.1 assigns Persistence's staging to Session, and required fix RF-7 at line 66 records that no admitted transition covers a durable write whose only change is a newly presented offer; [FR-01](../../../BACKLOG.md#fr-01) is applying the HF-10 required fixes to HF-07a, HF-07b and HF-08 in another worktree during this same sprint. The tables above state the ownership HF-03a line 49 fixes and mark the offer-presentation write as a seam rather than naming a transition letter for it. Every HF-07a and HF-07b line number cited here is a line at this base and re-fires when FR-01 or FR-02 integrates.

A third item belongs to the same seam and is recorded rather than answered: how a **successful** run reaches a closed durable state. BIBLE line 582 states that a final encounter completes a successful run and leaves its placement to Q-P12. At this base the only admitted lifecycle-closing transition is Transition D, whose fact is the terminal flag a death sets, and FR-02's own admission rule for a new run reads that the committed run is null or terminal. No cited source states what a completed successful run commits, and this section invents neither a transition nor a field for it. It is carried to the coordinator as a candidate question in this card's handoff.

**Seam 2: the four-world target and its numbers.** The four-world target, the rebuild-each-run power and the permanent discoveries are mapped above from the Bible and the accepted discovery, and nowhere else. No level, route, exit topology, world order, encounter count or duration tuning is invented, and every number the loop would need that no source states is a row in the parameter table under a question ID. Where a source fixes a number — four worlds, two destination offers, one standard revival, four trees and eight endpoints — the table cites its line; where it does not, the table says `unset`.
