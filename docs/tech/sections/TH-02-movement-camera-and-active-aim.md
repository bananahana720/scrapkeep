## Contract

### What this section fixes

It fixes ten movement and aim states across three concurrent families, plus three cross-state modifiers; what each carries and who owns it; the complete set of module interfaces movement, camera-relative intent and active aim use and the edge each travels on; the order in which one tick resolves intent, movement, aim, contact and publication; sixteen ordering rules; twelve edge cases and nine failure modes stated as required behaviour; and twenty-eight tunable parameters, each either carrying a source line or gated on a question ID. It fixes no number that no cited source states.

It is not a runtime. A state named here has never been entered, an interface named here has never been called, no pose has ever been resolved, and no engine, browser or build ran for it.

### Movement and aim states

The movement and aim families exist inside TH-01's RL2, the only loop state in which gameplay time advances, and nothing here advances it outside C-TICK (TH-01 lines 36, 128; HF-04a lines 20, 34). The capability family is where a state is decided outside RL2: MA-09's selection is made at TH-01's RL4 intermission, where Session rebuilds `EffectiveBuild` from all current selections, and the state is entered when that rebuild is installed at the Session-authorized boundary TH-01's IF-21 places between RL4 and RL2. It then holds inside RL2 and advances nothing by itself. Step MR.1 walks that selection at RL4 and MI-20 the install. TH-01's RL7 revival hold is not ticking (TH-01 line 41): a state below may be carried across it, but no movement, aim or contact advances while it holds, and play resumes only through O4 once the spend is acknowledged. The three families are concurrent: exactly one movement state, exactly one aim state and either the presence or the absence of the capability modifier hold at any committed tick.

### Owned data

This contract reads and writes exactly the records the carried-state table assigns, through the interfaces above, and nothing else.

1. **Encounter writes `EncounterState`, `TickState`, `AttackLedger`, `EncounterRandomState` and `EncounterInbox` and no other record.** It owns the committed gameplay pose, the movement intent, the air-action budget, the authoritative aim pose and the gameplay reference basis. It receives the capability set, the definitions and a seed as values and holds no writable `RunState` alias (HF-03a line 46). Its records end at `retire`.
2. **CollisionQueries writes `CollisionWorldState` and `QueryBatchState`.** It is the sole application module that drives or interprets physical-body updates, it owns query ordering and the identified post-movement world, and it returns movement resolutions, contact interpretations and attack query results. It commits no pose, applies no damage and awards nothing (HF-03a lines 33, 47, 61).
3. **InputAdapter writes `PhysicalInputState` and `InputContextState`.** Clearing physical input cannot mutate a prepared action, a pause state, a save or the run, and an input callback only submits a request (HF-03a line 50; HF-04a line 46).
4. **Session writes `SessionControl`, `RunState`, `ProfileState`, `EffectiveBuild` and `PendingTransition`.** For this contract it rebuilds the capability set from all current selections so that a removed transformation stops contributing and repeated swaps accumulate nothing, and it installs that set as values (HF-03a line 57; TADR-002 line 32; BIBLE line 552).
5. **ContentAdmission writes `CatalogueAdmissionState` and `CatalogueRegistry`.** The run's pin selects a revision without modifying the catalogue; definitions reach Encounter only as self-contained values or handles whose reads call nothing (HF-03a line 48; HF-03b line 68).
6. **Persistence writes `PreferencesRecord` and its other three records, and it alone stages or replaces them.** A settings change uses its own separately versioned document, never holds a gameplay transition and is never held by one (HF-03a line 49; HF-07b line 175 as cited by TH-01).
7. **Presentation writes `PresentationState` and `FeedbackState` from published values.** The camera, the reticle, the interpolation pair and every cosmetic impact response are display state. Presentation performs no physics query, chooses no target and marks no attack applied; view bindings are not actor ownership (HF-03a lines 37, 51; HF-03b line 79).

### Growth clearance and optional transformation

**Clearance.** Growth adds physical presence and must preserve ordinary route clearance and the pleasure of steering; practical route clearance survives the increasing clutter; and level design must test the positional movement loop at ordinary maximum growth (BIBLE lines 481, 511, 487). The runtime obligations that follow are MO-10 to MO-12: the extent is a value, it changes only at a committed boundary, it is resolved through CollisionQueries, no handling penalty or mass cost attaches to an ordinary action, and a trapping passage is a content defect rather than a runtime special case. What the ordinary maximum envelope is, and therefore what a route must admit, is unset under Q-P22. Whether and how the extent grows during a live encounter as material is collected belongs to TH-05 with Q-P22's envelope and Q-P10's allocation; this section fixes only the boundary conditions any answer must satisfy.

**Transformation.** Optional transformative items may replace movement or attacks provided the player can still understand reachable routes and consequences (BIBLE line 485), and optional transformations can replace attacks or movement with the effective result rebuilt from current selections (BIBLE line 552). MO-13 fixes the integration: the same `request_equipment_change`, `EffectiveBuild` rebuild and `install_effective_build` path TH-01 uses at RL4, with the published snapshot carrying the capability set actually in force so the display can explain what stopped working. Which transformations enter the first content scope is unset under Q-P22; compatibility rules are unset under Q-P14; inventory and slot limits are unset under Q-P19. No transformation adds a module, a command, a record or an edge, and a transformation that required one would be a contract revision, not an item.
