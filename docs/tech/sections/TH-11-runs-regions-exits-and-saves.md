### Level and world identities

A run's routing is expressed entirely in domain IDs, opaque within-run keys and one ordinal. No identity below is a new field; each names the HF-07a row that already carries it. `Resolves` states whether the value is a catalogue reference that must resolve as the pair of `content_revision` and the ID (HF-05 line 27), or an opaque string the save owns and the catalogue never sees.

| ID | Identity | Durable carrier | Resolves | Stable across | Source |
| --- | --- | --- | --- | --- | --- |
| ID-01 | Run identity | `run.run_id`, one per aggregate | No; opaque token, never resolved through the catalogue | The run's whole life including its terminal state; replaced only by starting a new run | HF-07a line 101; HF-07b lines 44, 121 |
| ID-02 | World identity, that is, run-region identity | `run.checkpoint.route[].destination_id` for every accepted region | Yes; the region definition is never serialised | The content revision the run is pinned to | HF-07a line 150; BIBLE line 578 |
| ID-03 | Route position of a region | `run.checkpoint.route[].sequence`, ascending from 0 with no gaps | No; an ordinal within this run | The run | HF-07a line 149; HF-07b line 79 |
| ID-04 | Entrance identity | `run.start.entrance_id` before any level completes, then `run.checkpoint.next_entrance` | Yes | The content revision the run is pinned to | HF-07a lines 114, 166 |
| ID-05 | Level identity | **None of its own.** A level is identified positionally by the entrance it begins at, ID-04, and by the `run.checkpoint.generation_decisions[].scope_id` the generator recorded its decisions under | The `scope_id` is opaque; the entrance resolves | The `scope_id` is stable within the run | HF-07a lines 153, 166 |
| ID-06 | Offer identity | `run.checkpoint.offered_choices[].offer_id`, unique within the run, with `run.checkpoint.route[].offer_id` naming the offer an accepted region came from or null when it followed none | No; an opaque within-run key | The run | HF-07a lines 144, 151 |

**A level has no durable domain identity, and that is the contract rather than a gap.** The envelope stores the entrance a run resumes at and the generation decisions a scope recorded; it stores no level ID, no level index within a region and no count of levels completed. Three consequences follow and each is load-bearing below. A completed level is expressed as the advance of `run.checkpoint.next_entrance` and by nothing else (HF-07a line 166; HF-07b line 80). Progress within a region cannot be counted from the save, so no rule here may depend on "the third level of world two"; what the save can answer is which region the run is in, which entrance it resumes at, and which decisions that scope recorded. And a level's own content is reproduced from `generation_decisions` and `rng_state` as what actually happened, never re-derived from a seed alone (HF-07a rule 4 at line 63). Whether the producing content card later wants a level domain ID is Q-P23's and would be a revision of HF-07a, not of this section.

**A world identity is a catalogue reference and a route entry, in that order.** `run.checkpoint.route` records the destinations the run actually took (HF-07a line 148). The number of worlds a successful run crosses is a Bible fact at line 578 and is not derived by counting that array at runtime; the array is the record of what happened, and a run that ended early holds fewer steps without becoming invalid.

### An onward exit is not a world choice

BIBLE line 580 states both in one paragraph, and they differ in every property that matters to the durable record. `RX-08` is the one property they share.

| ID | Property | Onward exit, inside a region | World choice, at a region boundary |
| --- | --- | --- | --- |
| RX-01 | What is chosen | The next level's entrance inside the current region | The next run-region |
| RX-02 | Runtime state it is made in | TH-01 RL5 | TH-01 RL6 |
| RX-03 | Options presented | Exit topology and eligibility are open: Q-P12 | Exactly two randomly selected eligible destinations, BIBLE line 580 |
| RX-04 | Route effect | None. `run.checkpoint.route` gains no step, because a step's `destination_id` is a run-region | One step appended: the next `sequence`, the chosen `destination_id`, and the `offer_id` it was taken from |
| RX-05 | Entrance effect | `run.checkpoint.next_entrance` advances to the entrance after the cleared level | `run.checkpoint.next_entrance` becomes the accepted region's entrance |
| RX-06 | Offer record | An `run.checkpoint.offered_choices[]` entry **only when options were presented**; a single forced continuation presents no options and stores none | Always an entry, with exactly two `option_ids` |
| RX-07 | `offer_kind` | An exit kind, distinct from the world-destination kind; the token vocabulary is the producing content card's | The world-destination kind, which BIBLE line 580 separates from an item reward offer |
| RX-08 | Transitions that carry it | A to present the offer, B to answer it, A to bank the cleared level | The same three, unchanged |
| RX-09 | Encounter effect | Replacement across a level boundary, TH-01 LO-08 | Replacement across a world boundary, TH-01 LO-08, the same six steps |

Three rules follow and none of them adds a field.

1. **A route step means an accepted region, never an accepted level.** `run.checkpoint.route[].destination_id` is the domain ID of a run-region (HF-07a line 150). Appending a step for an in-world exit would make the array's meaning ambiguous and would make the number of route steps disagree with the number of worlds the run crossed. An in-world exit therefore shows up in the save only as the advanced `next_entrance` and the new scope's `generation_decisions`.
2. **Any presented set of options is an offer, whatever it chooses between.** N3's stability rule is a property of `run.checkpoint.offered_choices`, not of world transitions (HF-07b line 131). An onward exit that presents two or more exits is an offer and is bound by every rule in the next subsection; an onward exit with one forced continuation is not, because nothing was offered. Which of the two an exit is remains Q-P12's, and this section fixes only that the answer selects between these two already-specified behaviours and needs no third.
3. **The world choice is independent of item rewards.** BIBLE line 580 says so, and the envelope carries it: a world-destination offer and an item reward offer are separate `offer_kind` values in the same array (HF-07a line 145), so a reward offer answered in the same intermission is a different `offer_id` with its own `option_ids`, and neither can be mistaken for the other on restore.

### Stable offered options across saves

BIBLE line 584 requires already offered choices to remain stable. Four rules make that checkable, and the fifth states the window in which the requirement does not yet bind, which is what makes the other four honest.

| ID | Rule | Mechanism | Source |
| --- | --- | --- | --- |
| RS-01 | The options presented are the options stored. `option_ids` holds the actual options in the order they were presented. | The field stores the outcome, not the input that produced it. | HF-07a line 146; TADR-004 line 26 |
| RS-02 | A stored offer is restored by value and never regenerated. No generator is consulted on restore, and a seed never replaces a stored outcome. | Validate rejects a candidate in which a committed offer's `option_ids` differ. | HF-07a rule 4 at line 63; HF-07b lines 79, 88, 131 |
| RS-03 | `chosen_option_id` moves from null to a member of `option_ids` exactly once and is never rewritten. | Validate requires a non-null value to be a member of the stored `option_ids`. | HF-07a line 147; HF-07b lines 88, 131 |
| RS-04 | The presentation of an offer is durable before it is answerable. Presenting commits through Transition A's offer-only path, riding in the completion candidate or committing as a second Transition A write whose only change is the entry; answering is Transition B. | The offer-only path's validate requires the new `offer_id` absent from the committed entries, a null `chosen_option_id` and an unchanged `next_entrance`, because presenting an offer is not taking it. | HF-07b lines 76, 79, 81; HF-10 line 66 |
| RS-05 | Stability binds from the acknowledgement of the presenting transition, not from the moment pixels appear. A hold at stage 1 or 2 of the presenting Transition A leaves no stored offer, so a restore re-presents the transition and may generate the options afresh; a hold at stage 3 or 4 leaves the offer durable but unreleased and the transition stays held rather than presenting an unproven offer as answerable. | N3 binds only an offer the committed record already holds. | HF-07b lines 42, 81, 131 |

Two things the stability rule is not. It is not a claim that the same two destinations would be generated twice: it is the reason the generator is never asked twice. And it is not an ordering guarantee over `run.checkpoint.rng_state`; the stored options are what keep a presented offer fixed, while the stored generator state is what keeps a later draw from repeating a consumed one (HF-07a lines 143, 156).

Four consequences follow from those four rows and the admitted envelope. None invents a value.

1. **A successful run holds exactly four route steps and takes exactly three world transitions.** Sequence 0 is the fixed starting region, whose `run.checkpoint.route[].offer_id` is null because it followed no offer (HF-07a line 151). Sequences 1, 2 and 3 each carry a non-null `offer_id` naming the world-destination offer they were taken from. Four regions and four worlds agree, which is what BIBLE line 578 fixes and DISCOVERY line 11 repeats.
2. **Eligibility is computable from the committed route alone and needs no new field.** The unvisited pool at a transition is the set of catalogue run-regions minus every `destination_id` already in `run.checkpoint.route`. The fixed starting region is in that array as sequence 0, so the no-repeat rule excludes it without a separate flag. No `visited` field, no pool snapshot and no eligibility cache enters the envelope, and HF-07a needs no revision for this answer.
3. **The third world transition offers the whole remaining pool.** With five catalogue regions and the first fixed, the pool is four at the first transition, three at the second and two at the third. At the third, "two randomly selected eligible destinations" and "every eligible destination" are the same set, so the draw selects nothing. The offer is still stored, still carries two `option_ids` and is still bound by RS-01 to RS-05, because the stability rules are properties of the stored array and not of how the options were chosen. The case is RE-05 below.
4. **Exactly one catalogue region is unvisited in every run, and it is never the fixed starting region.** That is a direct consequence of five candidates, a fixed first and three of the remaining four; it is stated here as a routing fact, not as a content judgement about which region is missed.

**A content consequence, gated on the content cards and not authored here.** Under RT-03 every region that can occupy the fourth position needs a finale-capable boss variant. Under RT-01 the fixed starting region can never be fourth, so the regions that need one are the catalogue regions other than the fixed starting region. Whether a finale-capable variant is a separate boss, a graded variant of the region's ordinary boss or something else is the enemy and boss roster's decision under [Q-P25](../../../BACKLOG.md#q-p25), and the region definitions themselves are [Q-P23](../../../BACKLOG.md#q-p23)'s and the content cards'. This section authors no boss, no variant and no grade.

### Owned data

Routing reads and writes exactly the records the carried-state table assigns, through the interfaces above, and nothing else.

1. **Session writes `RunState` and settles each accepted route step, offer answer and exit once** (HF-03a line 57). It appends a route step only on an answered world-destination offer, advances `next_entrance` only from a completed level's accepted results, and never writes a durable record itself.
2. **Persistence alone stages, validates, commits and acknowledges every routing candidate and writes its file** (HF-03a line 49; HF-07b lines 37 to 40). Session supplies the accepted inputs on D04 and waits. HF-10 required fix RF-6 at line 64 recorded the one admitted scenario step that read otherwise; FR-01 applied it.
3. **ContentAdmission owns the revision every `destination_id`, entrance ID and `option_ids` member resolves against** (HF-03a lines 34, 48). The run's pin selects a revision without modifying the catalogue, and a replacement candidate never edits cached Resources a live run still references.
4. **Encounter writes its five records and holds no routing fact.** It receives the entrance, the build and the complete definition set as values at `initialize_encounter` and keeps no writable `RunState` alias (HF-03a line 46). A level's interior position is not the run's position.
5. **Presentation writes its two records from published values and holds no route authority.** A map view displays the stored `option_ids`; it rerolls no route offer, chooses no destination and records only a `UiRequest` value Session reads on D06 (HF-03a line 51; HF-03b line 79; TADR-002 line 30).
6. **InputAdapter and CollisionQueries hold nothing durable and nothing routing-related.** Input frames are never restored from a save and a collision world is discarded with its level (HF-03a lines 47, 50).
