## Contract

### What this section fixes

It fixes five HUD snapshot classes with their producer, carrier, callback family and durability; the seven Bible answers mapped one by one onto a published carrier; twelve HUD rules; seven dashboard states with the published values each is rebuilt from, the refusal each must show and the durable trace each does or does not have; five rebuild rules; ten settings-ownership rules; fourteen focus-restoration and input-clearing rules; twenty-two interface rows, each naming one HF-03a command, published result or owned record on one HF-03b edge; the owned-data partition and the closed list of durable fields a view may present; seven ordered procedures; twelve edge cases; nine failure modes; thirty-one tunable parameters, each carrying a source line or a question ID; and four paper walks with a named outcome each.

It fixes no screen layout, no anchor position, no control geometry, no font or target size, no viewing distance, no display size, no controller device, binding or glyph, no scale value, no sensitivity range, no inventory capacity, no mount count, no respec price, no revival health value and no timing. Where the interface needs one of those, the rule below names what must be true of it and the parameter table routes the value to its question.

### Vocabulary

**Snapshot** is a detached immutable published value carrying its producer's identity, never a reader's copy of an owner's record (HF-03a line 56; HF-04a line 79). **Dashboard state** is a condition a view expresses, rebuilt from published values and the current opportunity every time it is shown and never stored (TH-07 PR-03 line 112; TH-08 EO-18 line 192; TH-04 AA-05 line 56). **Input class** is PD-02's vocabulary at its line 44 and is used unchanged here, because the accidental-cast guarantee is an assertion over rows of that type:

| Class | Meaning | May reach `submit_action` |
| --- | --- | --- |
| `navigation` | Moving interactive focus, opening or closing a view, or activating a control whose whole effect is navigation. | Never |
| `ui-request` | Activating a control that records a `UiRequest` value Session later reads (TH-01 IF-19 line 92). | Never |
| `control` | The pause, resume and capture work of O1 to O4 (HF-04a lines 87 to 90). | Never |
| `gameplay` | An action request routed into the encounter inbox at RL2 (TH-01 IF-14 line 87). | Yes, and only here |
| `display` | Presentation showing an existing published result (HF-04a F-PROCESS line 44). | Never |

### Algorithms and update order

1. **UA-1, one HUD refresh.** Encounter publishes at C-TICK P6. Session reads the identified results on D01 under F-PROCESS (UI-06), then supplies them to Presentation on D06 (UI-07). Presentation interpolates within the pair it holds. No step of this procedure runs inside C-TICK, and neither reader adds a tick. (HF-04a lines 67, 79; HF-03a line 39.)
2. **UA-2, one dashboard-state rebuild.** Read the published snapshots of HS-4; read the authorized opportunity as a run fact in the same snapshot; rebuild each of DS-1 to DS-7 from those inputs and the admitted definitions supplied as values; display. Nothing is stored between rebuilds and nothing is carried from the previous display. (DR-01, DR-02.)
3. **UA-3, a modal transition out of gameplay.** Read the notification before routing it (UI-01), then O1 (UI-03), then O2 (UI-04), then O3 (UI-05), then show the interactive view (UI-07). A notification received mid-tick is latched and this sequence completes at the first non-reentrant control boundary before another tick. The order is not an optimisation: O3 alone cancels nothing. (HF-04a lines 92, 94; FI-01, FI-02, FI-07.)
4. **UA-4, a view's request.** The control records a `UiRequest` value in `PresentationState` under F-INPUT (UI-10); Session drains it on D06 under F-PROCESS (UI-09); Session validates the run-state gate and the opportunity on its own record; it admits the request through UI-11, UI-12 or UI-15, or refuses it and shows the scoped diagnostic through UI-08. The view neither performs nor retries the mutation. (HF-03b line 79; TH-07 PR-04 line 113; DR-03.)
5. **UA-5, a settings change.** UA-4 to the point of admission, then `request_preferences_change` on Session's record and `commit_preferences` on D04 (UI-15), then the four stages over the preferences document, then present the new value while focus stays where it was. Admitted at RL4 and RL9 only; the completion arrives as F-ASYNC. (SO-02, SO-03, SO-05, SO-08.)
6. **UA-6, resume.** Check readiness, perform O1 again to consume the resume or capture action and require neutral re-arm, restore the prior eligible state, and unpause last (UI-03 then UI-05). The next eligible C-TICK is the first gameplay advance, and its first step is UI-20, not UI-18. (HF-04a line 90; FI-08.)
7. **UA-7, view release at encounter replacement.** Session retires the outgoing identity, releases the outgoing views and cue state through UI-17, clears the interpolation pair, binds the new views through admitted handles passed as values, publishes the initial same-encounter snapshot, and restores input through O4. The intermission's order is stated once and reused rather than restated: an admitted equipment or respec change produces one whole rebuild (UI-14) and at most one install, and that install crosses D01 as `install_effective_build` under F-CONTROL (UI-13), or as `initialize_encounter` under F-LIFECYCLE when the next encounter does not exist yet. Level completion is HF-07b's Transition A reached from TH-01 RL3; the revival spend is Transition C reached from RL7; a run closing either way is Transition D reached from RL8. This section names the same phases, callback families and transitions as TH-07, TH-08 and TH-11 already do and adds none.
