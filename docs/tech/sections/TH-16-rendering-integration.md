## Contract

### What this section fixes

It fixes six view states and two cross-state modifiers; ten committed-result consumption rules; nine interpolation rules; nine scene-disposal rules; nine reusable-effect-resource rules; eight definition-to-view mapping rules; twelve telegraph-readability rules; ten silhouette-and-clearance qualification rules; twenty-four interface rows, each naming one HF-03a command, published result or owned record on one HF-03b edge; seven owned-data rules; twelve ordering rules; fourteen edge cases; nine failure modes; and thirty tunable parameters, each carrying either a source line or a question ID. It fixes no number that no cited source states.

It is not a runtime. No view named here has been bound, no snapshot named here has been interpolated, no telegraph named here has been drawn, no effect resource named here has been reused, no scene named here has been freed, and no engine, browser or build ran for it.

### Where this section sits

The admitted siblings already fix that Presentation consumes published values and decides nothing (HF-03a line 51; HF-03b line 79), that it interpolates within one snapshot pair and never extrapolates (HF-04a line 79), that its interpolated transform never feeds the query world (HF-03a line 47; TH-15 line 79), that one descriptor serves damage and every visual consumer (TH-03 line 136), that a cue marks nothing applied (TH-04 line 174), that a view holds no gameplay generator (TH-14 line 60), and that a required telegraph which cannot be drawn holds the encounter (HF-04a line 100; TH-03 line 217; TH-06 line 298).

They do not fix what a view holds between two deliveries, what "release" leaves behind, how one effect resource may be shared by two actors and two encounters without becoming a second identity, which key maps a definition to a view, or what a reviewer compares a drawn telegraph and a drawn silhouette against. **This section specifies exactly those five things and adds no sixth.** Every rule below is a consequence of an admitted clause or of an approved Bible line; where the consequence bounds an answer Q-E04, Q-P30 or Q-P32 has not yet given, the bound is stated as a gate on that answer and never as the answer.

### Owned data

Rendering and effect integration reads and writes exactly the records below, through the interfaces above, and nothing else.

1. **Presentation writes `PresentationState` and `FeedbackState`, and no other module writes them.** `PresentationState` holds view bindings, previous and current result copies, interpolation, camera, UI display state and pending UI request values; `FeedbackState` holds cosmetic effects, animations, audio voices and presentation-only cue-consumption state. Both are replaceable from published results. A view binding is not actor ownership, cue consumption settles no reward and marks no attack applied, and preferences are consumed as a snapshot rather than mutated through the display copy. Neither record is a generator position, neither has a durable projection, and neither may hold a writable alias into another owner's record (HF-03a lines 37, 51, 56; TH-14 line 60; HF-07a line 60).
2. **Encounter writes `EncounterState`, `TickState`, `AttackLedger`, `EncounterRandomState` and `EncounterInbox`.** The committed pose, the committed descriptor, its targets, its drawn outcome and its applied-result identity are Encounter's, published at P6 and read by a view only as detached values. A view writes none of them, and Encounter holds no view (HF-03a line 46; HF-04a line 67; TH-03 line 48).
3. **CollisionQueries writes `CollisionWorldState` and `QueryBatchState`.** Presentation performs no physics query, its interpolated transform never feeds this world, and there is no visual-transform writeback; a body transform is a physical-world projection and never a gameplay pose (HF-03a lines 33, 47; HF-04a line 69; TH-15 lines 79, 81).
4. **Session writes `SessionControl`, `RunState`, `ProfileState`, `EffectiveBuild` and `PendingTransition`.** It alone routes results to views, installs a rebuilt capability set, settles an accepted result once and owns every lifecycle transition; no view and no cue settles anything in the run (HF-03a lines 45, 57; TH-01 lines 130, 139).
5. **ContentAdmission writes `CatalogueAdmissionState` and `CatalogueRegistry`.** A scene, effect, material, animation or audio definition is an immutable admitted value delivered through Session as a handle, with no accumulating per-run field on the admitted path; Presentation holds no mutation callback into ContentAdmission and resolves no ID (HF-03a line 48; HF-05 lines 31, 35, 37).
6. **InputAdapter writes `PhysicalInputState` and `InputContextState`.** A UI control records a `UiRequest` value in `PresentationState` rather than in either of these; clearing physical input mutates no prepared action and no view (HF-03a lines 36, 50; HF-04a line 46).
7. **Persistence writes `SaveTransactionState`, `DurableAggregate`, `PreferencesRecord` and `RecoveryState`, and writes nothing that expresses a rendered fact.** The only durable value any rule above reads is the motion-comfort setting at HF-07a line 189, consumed as a snapshot; committing it is the transition named in Seam 2 and is not performed here (HF-07a lines 60, 189; HF-03a lines 49, 51).
