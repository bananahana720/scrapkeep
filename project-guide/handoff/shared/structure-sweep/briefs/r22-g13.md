## The unit

Three small faults in the scripts that guard a push and start git. Each part is its own commit. None changes a file the game loads.

**Part 1: the pre-push hook lists changed files in a form it cannot always read back** (`LEAD-97`, first half). `scripts/hooks/pre-push.mjs` asks git for the changed paths with `git diff --name-only` (three calls) and splits the answer on newlines. Git prints a path that holds a non-ASCII letter, a quote or a control character inside double quotes with escapes, so such a path is then not found in the pushed tree and the push stops with a message about a missing path instead of the file being checked. Ask for the list with `-z` and split on the NUL byte, in every place the hook (and any helper it shares with CI, `scripts/ci/affected.mjs` among them) lists paths. Unit G11 already reads the pushed tree this way (`treeFiles` in `scripts/ci/affected.mjs`, `git ls-tree -r -z`); use the same form and keep one function that turns a `-z` answer into paths, not two. The hook stops on a path that holds a newline or a carriage return; keep that. Test with a scratch repository that pushes a file whose name holds a non-ASCII letter and one whose name holds a space and a quote: both are checked, and neither stops the push.

**Part 2: the hook's temporary copies outlive a stop signal** (`LEAD-97`, second half). The hook copies the pushed `.js` and `.mjs` files into a folder under the system's temporary folder and removes it in a `finally`. A stop signal (Ctrl-C during a push, or git ending the hook) skips the `finally`, and the earlier writer found a signal listener cannot run while the hook sits in a blocking child call. Weigh at least these: (a) run the hook's child commands without blocking (the helper `runProcess` in `scripts/lib/proc.mjs` does that) so a listener can remove the folder and then end with the signal's status; (b) keep the blocking calls and make the leftover harmless and self-cleaning: one fixed parent folder for the hook's copies, and at each start the hook removes copies older than a stated age that no live process owns; (c) leave it, with the reason. The hook must stay inside its time budget (nine seconds; it prints the time it took) and must behave the same for a push that passes. Take the one that adds the least code, and prove it with a test that starts the hook, stops it with `SIGTERM` in the middle of a child call, and then finds no copy left (or, for (b), finds it removed by the next start). Any cleanup must be unable to remove a folder it did not make: remove only folders whose name matches the hook's own prefix inside the folder the hook made them in, never a path read from a file or an environment variable without that check, and cover that with a test.

**Part 3: a git call that passes its time limit leaves a lock file** (`LEAD-92`). Since unit G10, `scripts/lib/git.mjs` kills a git call at once when it passes its time limit (`killSignal: "SIGKILL"`), so git cannot remove its own `.lock` files, and a later git call in that repository fails until someone removes the lock by hand. Two kinds of caller pass a limit: `scripts/sketch-nightly.mjs` gives `git status` ten seconds, and `scripts/card-runner.mjs` gives its `fetch` and `push` five minutes. For the reads (`status` and anything else that only reads), make git take no optional lock: pass `--no-optional-locks` (or set `GIT_OPTIONAL_LOCKS=0`) for those calls, inside the helper where a caller says the call only reads, or for the caller, whichever is smaller. For the two long network calls, give git a first polite stop (`SIGTERM`), a short stated grace, and only then the kill; `stopGroup` in `scripts/lib/proc.mjs` already does that for a process group. If that needs a non-blocking form of the helper, add the smallest one and move only these two callers onto it; do not rewrite `scripts/card-runner.mjs`'s other steps. Find every caller that passes a time limit to the git helper first and list them in the report with what each now does. Test with a stand-in for git (the tests of `scripts/lib/git.mjs` already inject `spawn`) and, for the stop-then-kill path, with a real child that ignores `SIGTERM`: it is dead after the grace, and one that honours `SIGTERM` is never sent the kill.

**Part 4: the safety hook cannot tell being run from being imported when its helper is missing** (`LEAD-93`). `.agents/hooks/safety-gate.mjs` loads `scripts/lib/cli.mjs` inside a `try` and ends with `if (helpers.isMain?.(import.meta.url) ?? true)`: when the helper cannot load, it acts as if it were the script being run, so a test or module that only imports the hook reads standard input and prints an `ask` line. The guard in `scripts/lib/cli.test.mjs` forbids reading `process.argv[1]` outside its list, so a second copy of the test for "am I the script being run" inside the hook is not wanted. Weigh: (a) when the helper cannot load, the hook decides from something that needs no helper and is not `process.argv[1]` (for one: whether standard input is a pipe carrying the tool call, which is how the host always runs it); (b) add the hook to the guard's list with a three-line local test, and say why the list grows; (c) leave it: the hook must fail towards asking, a missing helper means a broken checkout, and an import of the hook in that state is a test's problem. Whatever you pick, the hook run by the host with a missing helper must still print its `ask` line (it must never go silent and so allow a command), and that has a test. If the least-code answer is (c), say so with the reason and change nothing in this part.

Add no code comment except a tool-read line or a note on an engine or operating-system quirk. Do not change what the hook checks or which pushes it stops, apart from the paths it could not read before.

Stage files by name, never with `git add -A` or `git add .`. Any check, guard, test or tool you add or change must fail, not pass, when it cannot read, find or compare its input (a folder that does not open, an empty file list, an empty read, a failed `git` call, a pattern that does not compile, a missing argument): cover each such case with a test and name them in your report.
