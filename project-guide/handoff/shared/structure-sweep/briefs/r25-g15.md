**Background.** The Linux CI job for a pull request runs `node scripts/sketch-fast.mjs ... --no-base-check`, so it does not run a failing test on the base commit. Unit G14 added a rule for that case: a test that `project-guide/handoff/KNOWN-FAILING.tsv` (read at the `--base` commit) lists as red on `main` is named `known red on main`. The run still fails, because ruling bq says a ledger row never changes whether a run fails; when every red of the run is such a test, the run's last line is `sketch:fast fail: only known reds on main (<count>): <tests>` and the receipt's `main_red.only_known_reds` is true. The Gate's merge tool is meant to read that line to decide whether a red job on a pull request may be carried. It does not yet, because the reviews found the gaps below. A wrong `only known reds` line is the worst fault this code can have, so every part fails closed: when in doubt the run reports a new red.

**Part 1 (LEAD-134): every run of the test decides, not the rerun alone.** In `main()` of `scripts/sketch-fast.mjs`, `handle` passes only `confirm`'s rerun to `mainRed.settle`. If a listed test's first run fails a check its row does not name (or crashes, or is killed at its limit) and the rerun fails only the listed check, the test is marked as a known red and the first failure is never named. The gate's own ledger rule (`whatFailed(runs)`, now in `scripts/known-failing.mjs`) reads the first run and every rerun together. Give `settle` every run of the test in this invocation (the first run, in a warm batch or alone, and the rerun) and mark the test only when each of them qualifies on its own; otherwise it is a new red and the line says so. Say what a first run inside a warm batch can and cannot tell you about one test's failing lines, and fail closed where it cannot. Tests go through the real shapes: first run bad and rerun listed; first run listed and rerun bad; both listed; first run in a batch.

**Part 2 (LEAD-134): the words a red-on-main row may use.** The ledger checker (`parseLedger`) allows, in the check column of a row that carries the red-on-main marker, a star (any text inside one check) and the reserved words `ERROR-LINE` and `TIME-OUT`. Each can cover a failure nobody saw on `main`: a star matches other checks of the same test, `ERROR-LINE` lets any error line through, and `TIME-OUT` can never apply to a run that must end normally to be marked. Refuse all three in a row with the marker, with a message that says what to write instead (the exact check as the test prints it). No row that exists today uses them; confirm that and keep the two rows as they are.

**Part 3 (LEAD-134): the test calls the code it guards.** The test for a log dropped before the rule reads it copies the `{ output, ...run }` strip that `keepRed` does, because `keepRed` lives inside `main()`. If `keepRed` ever dropped the failure record too, the test would not notice. Move `keepRed` (or the part of it that decides what survives) to an exported function the test calls, with no change in what it does.

**Part 4: the time budget does not hide.** `scripts/ci/check-budget.mjs` wraps the CI job's call and reports `OVER_BUDGET` when the job ran past its limit; when the child also exits non-zero it reports `FAIL` only, so a job that is both red and over its 900-second budget shows the `only known reds` line and no sign of the overrun. Report both facts in that case (the exit code stays the failing one) in a fixed form a tool can read, and add the case to its test.

**Part 5 (LEAD-132): one parser for the ledger.** `scripts/ledger-audit.mjs` keeps its own parser of `KNOWN-FAILING.tsv` beside `parseLedger` in `scripts/known-failing.mjs`. Find every place the two differ (run both on the real ledger and on the malformed rows in the tests), move the audit onto the one parser, and delete the second. If the audit needs something the owner does not return, add it to the owner's result; do not keep a second reader for it.

**Part 6 (LEAD-118): small test gaps.** `scripts/lib/proc.test.mjs` does not list a few inputs `processId` already refuses (`-0`, a BigInt, a boxed number, an object with `toString`, non-ASCII digits, `0x10`, the infinities): add them, and fix `processId` only if one turns out not to be refused. `scripts/hooks/pre-push.test.mjs` calls `process.getuid()` directly, which does not exist on Windows: skip those cases there, as the hook itself does.

**The page.** `project-guide/handoff/GATE.md` states the rule; keep it exact after parts 1, 2 and 4 (a test pins the page against the code: extend it). Do not write that a job goes green.
