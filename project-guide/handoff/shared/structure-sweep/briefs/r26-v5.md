Do not make a dependency invisible to the lint without removing it: dropping a type so a class name is no longer written, building a path from pieces, or loading by `uid://` hides the load from the graph and is not a fix. 

**The problem.** A model file (`.glb`) is loaded, checked, cached and turned into mesh parts in more than twenty places, each hand-written: its own `load` call, its own cache dictionary, its own warning when the file is missing, its own walk over the scene to find the mesh. `src/presentation/model_variants.gd` is the owner that already does this for thirteen callers, and `EnemyCasting.parts()` does it for some enemies; the survey counts 22 loaders outside the first and 25 enemy loaders that could use the second (the two counts overlap; count them yourself). A change to how a model is loaded (a fallback, a warning, a cache reset between tests, a level of detail) has to be made in every one, and is not.

**Decide the one owner and where it lives.** Weigh at least three shapes and say why you chose: one loader that returns the parts of a model file with one cache and one warning, which `ModelVariants` and `EnemyCasting` both call; `ModelVariants` as the only owner with `EnemyCasting.parts()` as its caller; or the two kept apart with a stated border between them. Then its directory: the survey suggested moving the loader to `src/core`, written before the layer order existed. Decide with the record: lower layers (`combat`, `boss`, `world`, `build`) load it, so in `src/presentation` each caller is an upward pair on the L20 list; but `src/core` is for facts and state, not for drawing. If the loader depends on nothing above `core` (it reads a file and returns mesh data) and you can state in one sentence why reading a model file is a shared fact, moving it down removes those pairs; if it needs presentation's materials or variants, it stays and the callers are handed their parts. Measure both with `node scripts/sketch-lint.mjs --sketch core-loop --layers` and give the numbers. Do not create a new directory.

**The baseline exists: use it.** `tests/mesh_census_test.gd` pins every mesh the game builds (299 at last count) by an exact hash of its vertex data on the recording platform. It must pass unchanged, with the same pin file, after every commit of this unit; a loader that returns a different mesh, a different surface order or a different material slot shows there. Before you change a loader, check the census covers the models it loads (run it and search its pin for the model's name); for any it does not cover, add the model to the census in a first commit that passes on the base.

**Move the callers in one batch and delete what they replaced.** Each hand-written loader becomes a call of the owner; its private cache dictionary, its warning text and its scene walk are deleted, not left beside the call. The differences are the work: a loader that scaled, re-centred, picked a named child, merged surfaces or swallowed a missing file did something the owner must either offer as a stated option or the caller must keep doing after the call. List every difference you found, by loader, and where it went. Do not merge two loaders whose difference is a design fact (a boss model that must fail loudly when missing against scenery that may fall back). Caches: one, with one way to clear it between test files, registered where the shared-process test driver resets state (`tools/test_batch_driver.gd`); lint rule L14 will ask for it.

**What must not change.** Every mesh, material slot and warning a player or a test can observe; the moment a model is first loaded where that matters (a loader that warmed a model at boot must still warm it, or a first use will hitch: say which loaders warmed and that they still do); memory held by caches (one cache holding what twenty held is fine; a cache that now never frees what a per-stage cache freed is not: say what each old cache's lifetime was).

Each of these sent a unit back from review at least once. Check your work against every one before you hand in.
1. **A check that passes when it read nothing.** A test or tool you add or change must fail when it cannot read or compare its input: a folder that does not open, an empty file list, an empty read, a pattern that does not compile, a command that exits non-zero or prints nothing.
